## 1. 单文件 SMB 备份慢（性能瓶颈）

### 1.1 现象

从手机向 SMB 服务器备份大文件（尤其视频）极慢：单文件 1.47 GB 实测 **4.78–5.00 MB/s**（四路分片并行，单路约 1.28 MB/s），持续传输时 UI 卡顿。

用户诉求：从软件本身解决，**不接受"只调并发数"**；必须先定位瓶颈再改代码。

### 1.2 根因

通过 Profile/AOT 真机计时拆解（`[diag0]` / `[timing2]`）确认，瓶颈**不在分块大小、连接数或数据拷贝**，而在 **SMB2 报文签名**：

- 真机实际协商方言为 **SMB 2.1（`0x210`）**，签名算法为 **HMAC-SHA256**（此前误判为 AES-128-CMAC，已更正）。
- 每块 64 KiB 单连接墙钟 ≈ **48 ms**：本地读 ~13.6 ms（含主 isolate 排队假象）、encode ~10 ms（**其中 ~9.8 ms 是签名**）、等待响应 ~24 ms。
- `pointycastle` 的 SHA-256 把 8 字状态与消息缓冲存成装箱 `List<int>`，每个 32 位运算都经 `clip32`/`rotr32` 包装，输入按 4 字节逐字解包 → 64 KiB 报文签名约 **9.1–9.8 ms**，微基准仅 **6.78 MB/s**（同类实现合理应有 30–50 MB/s，属**实现低效**而非算法固有开销）。
- 4 连接并发 ≈ 79 块/s × 9.8 ms ≈ **0.77 s CPU/秒**，全部在主 isolate 串行 → 占用约 90% 算力，事件循环抖动（50 ms Timer 被拖到 130–240 ms）。

真机证据：

```
[diag0] negotiated dialect=0x210 (SMB210) sigRequired=false sigEnabled=true enforced=false
[diag0] sign benchmark alg=SHA-256/HMAC bytes=65008 rounds=10 avgUs=9147 throughput=6.78MB/s
[diag0] signing=ENABLED alg=SHA-256/HMAC setupRequired=false responseSigned=true
```

补充结论：
- `sigRequired=false`：**Samba 并未强制签名**（`server signing = default`）；客户端仅因 Session Setup 响应带 `SMB2_FLAGS_SIGNED`，就在 [smb2_session.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_session.dart) 的 `isSignatureSetupRequired() || signed` 分支为整条会话开启签名。
- 库作者本意默认不签名：`Configuration.isSigningEnabled = false`、`SmbTransport._signingEnforced = false`（硬编码）。
- 服务端单次写入硬上限 **64 KiB**（`SmbStreamConsumer.blockSize = 64936`），加大分块会触发 `STATUS_INVALID_PARAMETER`，此路不通。
- `SmbTransport.sendrecv` 全程持有 `sendrecvMutex`，一条连接同一时刻仅 1 个请求在途。

### 1.3 方案（决策：路线 C）

**路线 C：保留 SMB 签名，优化 HMAC-SHA256 实现。** 先做纯 Dart 热路径优化，把 65,008 B 签名稳定压到 ≤2.2 ms（≥30 MB/s）；未达标再评估 C-FFI（Android 原生 HMAC）。

- 仅改一个文件：[smb2_signing_digest.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_signing_digest.dart)
  1. 新增 `_MacLike` 抽象接口：`_PointyMac` 包装 pointycastle `Mac`，`_CryptoHmac` 包装 `package:crypto`。
  2. **SMB 2.0.2 / 2.1 分支改用 `package:crypto` 的 `Hmac(sha256, sessionKey)`**——其 SHA-256 全程使用 `Uint32List`，同长度输入快约一个数量级。
  3. **SMB 3.0/3.0.2/3.1.1 仍保留 pointycastle 的 `AES/CMAC`**，协议行为不变。
  4. `_CryptoHmac.doFinal` 用 `Uint8List.view(...)` 零拷贝视图交给 crypto，避免额外复制。
  5. 签名语义与规范一致：清签名域 → 置 `SMB2_FLAGS_SIGNED` → 计算 MAC → 前 16 字节写入签名域。
- `crypto: ^3.0.3` 已是 smb_connect 现有依赖，无需新增。
- 回滚实测零收益的 `extensions.dart` 三处 `setRange` 拷贝改写，删除全部临时诊断插桩（`SmbTiming`/`EncodeDiag`/`[timing*]`/`diagReconcileLog` 等）。

**未被采纳的路线**：A（关闭签名，非严格合规、降低完整性保护，仅作对照/可选模式，不作默认）、B（SMB 写路径拆分到多 isolate，改动量大，暂不做）。

### 1.4 结果（验收门槛全部达成）

签名微基准（65,008 B × 10 轮，Profile/AOT 真机）：

| 实现 | 耗时 | 吞吐 |
|---|---:|---:|
| `package:crypto` HMAC-SHA256 | 1,475 µs | **42.03 MB/s** |
| `pointycastle` HMAC-SHA256 | 9,680 µs | 6.40 MB/s |

- 加速约 **6.6 倍**；交叉验证 `sign cross-check crypto==pointycastle: true`（签名字节完全一致）。

大文件端到端（1,466,810,721 B，四路分片）：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 吞吐 | 5.00 MB/s | **19.477 MB/s** | **+289%（约 3.9 倍）** |
| 事件循环最大间隔 | ~136 ms | **72 ms** | 抖动收敛 |

- 正确性：远端 SHA-256 `324ee621c5e9aadbe1bbce89fc0fe46cfdaa3e9b360189f5742867cc816e8468` 与本地一致；远端大小一致。
- 无回归：reconcile 386 张照片全部匹配；签名仍开启、SMB2.1 验签通过。

| 验收门槛 | 目标 | 实测 | 结果 |
|---|---|---|---|
| HMAC 微基准 | ≥30 MB/s | 42.03 MB/s | ✅ |
| 大视频吞吐提升 | ≥30% | +289% | ✅ |
| 远端 SHA-256 一致 | 必须 | 一致 | ✅ |
| UI 事件循环抖动收敛 | 明显收敛 | 136→72 ms | ✅ |
| 小文件/失败重试无回归 | 无回归 | 386/386 | ✅ |

**结论：纯 Dart 阶段目标达成，无需进入 C-FFI / A / B 备选路线。**

### 1.5 遗留项（可选）

静态审查对本次改动提出三条完善建议（非当前故障）：
1. 明确 `_CryptoHmac.update` 的输入约束：当前只保存最近一次 `update` 的数据，多次调用会覆盖；现调用路径仅单次调用，故成立。建议支持增量输入，或用注释/断言限制「每次摘要只允许一次 update」。
2. `_CryptoHmac.doFinal` 结束后仍保留 `_data` 对最近报文的引用，直到下一次 `reset`；建议在 `try/finally` 中清空 `_data`/`_offset`/`_length`。
3. 补充签名单元测试：覆盖重复调用、非零偏移及切片输入、与 pointycastle 签名字节一致、篡改后验签失败、SMB3 AES-CMAC 不回归。

> 优先级（用户已拍板）：**单元测试最高，输入约束次之，内存清理最低**；三项均不影响已达成的性能指标。

## 2. listFilesWithSize 间歇性失败导致对账误判「已备份 0」

### 2.1 现象

日志中同一批相册反复出现：

```
[diag-smb] listFilesWithSize FAIL path="相机" err=The system cannot find the file specified.
（连续 7 个相册全部 FAIL）
[reconcile] 1791830725307 候选 387 → 已备份 0
```

远端清单间歇性全部失败，随后「与服务器核对」把所有已备份记录整体清空（**不可逆的数据损失**）。

### 2.2 根因

调用链：`SmbService.listFilesWithSize` → `_getConnection`（共享缓存连接，key = `host:username`，TTL 1 分钟）→ `connect.file(smbPath)` → `connect.listFiles(folder)`。

- 异常抛出点：[smb2_files_enumerator.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_files_enumerator.dart#L38-L59) 对目录发 `CREATE(FILE_DIRECTORY_FILE)`，status ≠ OK 时抛 `SmbException`。`The system cannot find the file specified.` 对应 `NT_STATUS_NO_SUCH_DEVICE/NO_SUCH_FILE/OBJECT_NAME_NOT_FOUND`。
- 注意：`connect.file()` 对 not-found **不抛异常**，只返回 `SmbFile.notExists`，所以错误只在 `listFiles` 处暴露。

日志证据（已核对历史 logcat）：

| 观察 | 结论 |
|---|---|
| 同一进程 03:16:46 全 7 FAIL；03:27:53 全 7 SUCCESS（相机106/原神109/漫画44/DJI6） | 排除「路径/配置不符」 |
| FAIL 间隔仅 8–13 ms（≤1 个往返）；SUCCESS 每个约 300 ms | 失败调用**没有**做真正的目录枚举，被服务端立即拒绝 |
| 03:36:13 同批全 FAIL，但该批用**全新连接**（`createConnection`）成功上传 387 项 | **问题在共享缓存连接**（全新连接不受影响） |
| 04:44:41 冷启动全 SUCCESS，`候选 387 → 已备份 387` | 失败是**间歇性**的，非确定性 |

放大路径（已由源码确认）：
- **已确认的软件缺陷**：`listFilesWithSize` 把所有异常吞掉返回空表；`reconcileWithServer` 把空表当作远端权威结果 → `replaceSynced(serverId, stillSynced)` **整体覆盖** → 记录被清成 0。与代码注释「网络异常时放弃、不改记录」的既定意图不一致。
- **最可能触发因素**：复用共享缓存连接，共享连接出现瞬时失败（假设，未最终定论；**不得写成已证实根因**）。
- `reconcileWithServer` 仅用 `testConnection`（IPC$ `listShares` 探活）前置校验，对 MyDoc 各相册 not-found 时**探活不足以拦截**。

### 2.3 方案（decision-complete）

**变更 1 — `listFilesWithSize` 区分「读取失败」与「远端为空」**（[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart#L167-L203)）
- 返回类型 `Future<Map<String, int>>` → `Future<Map<String, int>?>`：`null` = 读取失败（不可信）；`{}` = 目录不存在或为空（远端确实没有）。
- try 前先算 `smbPath`；`connect.file(smbPath)` 后 `folder.isExists == false` → 打印 `ABSENT` 并 `return {}`；目录存在才 `listFiles`，最多 3 次总尝试（首次 + 2 次重试），每次重试前 `_invalidateConnection` 并重新获取连接；重试耗尽打印含 `path/smbPath/share/rootPath/host/err` 的 FAIL 日志并 `return null`。
- 复用 `isConnectionError` 判断可重试性；not-found 族在「目录已存在」前提下同样视为异常参与重试。

**变更 2 — 对账「清单不完整即整轮放弃，不覆盖记录」**（[transfer_provider.dart](file:///e:/Code/Projects/MiPix/app/lib/providers/transfer_provider.dart#L143-L173)）
- 抽出顶层纯函数（便于单测，与 `UploadFailureGuard`/`uploadWithRetry` 同风格）：

```dart
/// 计算「核对后仍视为已备份」的路径集合。
/// 任一相册清单为 null（读取失败）→ 返回 null，表示本轮清单不完整、应放弃。
Set<String>? reconcileSynced({
  required Iterable<String> candidates,
  required Map<String, String> albumOf,                  // 本地路径 → 相册名
  required Map<String, Map<String, int>?> remoteIndex,   // 相册名 → 清单（null = 失败）
  required Map<String, int> localSizes,                  // 本地路径 → 大小；缺失 = 已删除/不可读
});
```

- `reconcileWithServer` 结果为 `null` → 打印「清单不完整（存在读取失败的相册），放弃本轮，保留现有记录」并 `return`，**不调用 `replaceSynced`**。
- 语义细节：本地已删除 → 丢弃记录；相册名为空 → 不参与对账；`size > 0 && remoteSize == size` → 保留。

**变更 3 — 备份路径遇到未知远端清单时的处理**

## 3. 增量备份「同名文件冲突」处理

### 3.1 现象

仅用「文件名 + 大小」判断远端是否已有待备份文件，会出问题：
1. 同名同大小可能内容不同 → 直接跳过会漏备份更新内容。
2. 同名不同大小可能发生覆盖 → 较大版本也可能被较小版本替换。
3. 不同相册中的同名文件对应不同远端路径，不应视为冲突。
4. 同一批次多个本地文件可能指向同一远端路径；只保留先处理的会**依赖遍历顺序**。
5. 远端清单读取失败若被当成「目录为空」，会在未知远端大小下继续覆盖。

### 3.2 判定规则（以**远端目标路径** = 相册目录 + 文件名为准）

| 情况 | 处理 | 提示 |
|---|---|---|
| 远端无该目标路径 | 正常上传 | 无 |
| 同名、大小不同、本地较大 | 上传并替换远端 | 「已用较大版本更新远端文件」（可选） |
| 同名、大小不同、远端较大 | 保留远端，拒绝上传 | 「远端已有更大的同名文件，本次未覆盖」 |
| 同名、大小相同 | 双方 SHA-256 后决定 | 见下 |
| 两相册各自同名 | 各按各自路径处理，都可上传 | 不提示冲突 |
| 同批次多个本地文件 → 同一远端路径 | 先比较大小，按规则择一，不依赖遍历顺序 | 未选中者给原因 |
| 远端清单/文件信息不可读 | **不假设远端不存在**；fail-closed 跳过受影响文件 | 「无法读取远端信息，未备份，请检查连接或权限后重试」 |

同名同大小哈希规则：仅对「路径相同 + 大小相同」的候选做 SHA-256（流式读取，不入内存）。相同 → 视为内容相同、跳过并标记已同步；不同 → **默认保留远端**、跳过本地并提示「同名同大小但内容不同，远端文件已保留」。

### 3.3 方案（实施要点）

- **新增 `TransferStatus.skipped`**（[models.dart](file:///e:/Code/Projects/MiPix/app/lib/models/models.dart)）：确定性结论（远端更大、内容不同、批次落选）记 `skipped`，**不计入 `failedUploadCount`**；信息不可知类（清单/哈希/本地不可读）仍记 `failed` + 原因以保留重试入口。`clearCompleted()` 将 `skipped` 与 `done` 一样作为可清除终态；同版本 JSON round-trip 保持状态（旧版本遇未知值 `orElse: pending` 仅保证解析不崩溃，**不代表降级语义安全**）。
- **被拒绝的文件不算「已备份」**：不写入 `syncedPaths`，留在「未同步」中待用户处理。
- **纯逻辑层**（[transfer_provider.dart](file:///e:/Code/Projects/MiPix/app/lib/providers/transfer_provider.dart)，与 `reconcileSynced` 同风格）：

```dart
enum PlanAction { upload, skipSynced, skipKeepRemote, skipBatchCollision, skipAlreadyActive, failUnknown, failLocalUnreadable }
class ConflictCandidate { final String localPath, albumName, remotePath; final int size; }
class ConflictDecision { final ConflictCandidate candidate; final PlanAction action; final String? message; final bool needsHash; }
class ConflictPlan { final List<ConflictDecision> uploads, probes, settled; }

ConflictPlan planConflicts({ required List<ConflictCandidate> candidates,
                             required Map<String, Map<String, int>?> remoteIndex });
List<ConflictDecision> resolveHashProbes({ required List<ConflictDecision> probes,
                                           required Map<String, String?> remoteHashes,
                                           required Map<String, String?> localHashes });
```

  - 阶段一：按远端路径分组 → 组内取最大本地文件（并列用 `localPath` 字典序打破，**与输入顺序无关**）→ 对照远端清单产出计划；清单为 `null` 的相册全部 `failUnknown`。
  - 阶段二：回填哈希。任一哈希为 `null` → `failUnknown`（**绝不视为「相同」**）。
  - 任意哈希失败/清单失败，**不对远端任何写入**。
  - 文件名匹配遵循 SMB 服务器实际名称比较规则（不可仅凭客户端字符串精确比较假设大小写不同即不同文件）。
- **远端流式哈希**（[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart)）：`Future<String?> hashRemoteFile(config, remotePath)`——`_getConnection` → `connect.file(...)` 确认存在并复核大小 → 对远端文件**只调用一次** `openRead(file)`，逐 chunk 喂 SHA-256，不反复 `openRead(file, start, end)`；哈希前后核对远端大小，累计字节数必须等于预期大小，否则返回 `null`；每次重试新建摘要状态。异常走 `isConnectionError` + `_invalidateConnection`，重试耗尽打印 `[backup][hash] FAIL ... err=...` 并返回 `null`。不复用 `readFile`。
- **本地流式哈希**（[photo_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/photo_service.dart)）：`static Future<String?> hashFile(String path)`——用 `Isolate.run` 读 `File(path).openRead()` 并流式哈希；返回摘要与累计字节数，须与开始时本地大小一致。**远端读必须留在主 isolate（socket 不可跨 isolate），只有本地哈希下放。**
- **冲突原因文案（固定）**：清单读取失败/远端哈希失败 → `failUnknown`；本地不可读 → `failLocalUnreadable`；远端更大 / 内容不同 / 批次落选 → `skipKeepRemote` / `skipBatchCollision`；`skipAlreadyActive` 不算失败也不创建重试记录。
- **结果对象**：`BackupResult` 增加 `int conflictSkippedCount`（`skippedCount` 语义仍为「已备份跳过」）；`allAlreadyBackedUp` 只看 `skippedCount`/`successCount`/`failedCount`，冲突跳过单独显示，避免把未备份冲突误报为「均已备份」。
- **UI 三处一致**（[transfers_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/transfers_screen.dart)、[photos_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/photos_screen.dart)、[photo_viewer_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/photo_viewer_screen.dart)）：新增 `skipped`（灰色 +「已跳过」）分支；`errorMessage != null` 时渲染 11px 次级原因文案（最多 2 行，此前**完全没有渲染**）；SnackBar 优先分支「N 项同名冲突未备份（详见传输列表）」。

### 3.4 结果与验证

## 4. 息屏后备份中断与保活锁

### 4.1 现象

大批量备份时息屏一段时间后再点亮：传输速度归零、进度条静止、任务既未明确完成也未明确失败（看似「卡死」）。

### 4.2 取证与根因

现场时间线（Redmi K20 Pro，`com.chesereri.mipix` 1.0.7+8）：

| 时间 | 事件 |
|---|---|
| 02:21:02 | 应用进程 28166 启动 |
| 02:29:06 | 息屏（`Going to sleep due to timeout`） |
| 02:29:13 | 进入 DOZE |
| 02:30:48 | **首条异常** `Unhandled Exception: Bad state: StreamSink is closed`（息屏后约 100 秒） |
| 02:30:48~02:32:03 | 同类异常密集出现，共 83 条 |
| 02:34:01 | 仍在重复抛出（取证时点） |

调用栈（节选）：

```
#2 SocketWriter.write (package:smb_connect/src/utils/socket/socket_writer.dart:16)
#3 SmbTransport.doSend (package:smb_connect/src/connect/smb_transport.dart:739)
#4 SmbTransport.sendrecv (...:666)
#8 SmbService._deleteRemoteIfExists (package:mipix_app/services/smb_service.dart)
#10 SmbService.uploadFileVia (...)
#11 TransfersNotifier.backupPhotos.runItem (package:mipix_app/lib/providers/transfer_provider.dart)
```

异常统计：`Bad state: StreamSink is closed` 83 次；`TimeoutException` 0；`SocketException` 0；`Connection reset` 4。**没有任何"网络不可达"类系统级错误**，全部表现为「socket 已关闭但仍在写入」。

**排除的猜想**（息屏+卡死时取证）：
- ❌ 不是 Doze 掐断网络：ping NAS 成功（0% loss，avg 19.3 ms）、WiFi 已连接 866 Mbps、445 端口可连。
- ❌ 不是应用被冻结/杀死：进程存活（CPU 仍在消耗）、**未持有任何 wakelock**、从未申请 WifiLock、不在电池优化白名单、全仓库无前台服务/WakeLock/WifiLock 实现。

**根因（两层叠加）**：
1. **触发层**：传输期间完全未申请 `WifiLock`/`PARTIAL_WAKE_LOCK`；息屏后无线省电导致 SMB over TCP 会话被断开（`SocketWriter.write → _Socket.add → StreamSink is closed`）。
2. **放大层**：断连后无法恢复并持续空转——
   - `isConnectionError()` **不识别** `Bad state: StreamSink is closed` 这类 socket 关闭错误 → 重试/重连逻辑不生效，文件被判失败，且异常**逃逸为未捕获异常**，批量任务无法收敛。
   - 缓存连接 `_getConnection` 挂了 `onDisconnect`，但**传输实际使用的 `createConnection` 没有挂**，连接死掉无人感知。
   - 没有「等待网络/屏幕恢复再续传」机制：每文件经历 15–30 秒超时空转（库内 3 秒 × 5 次重试 + `_stallTimeout = 30s`），大文件量下进度条冻结数小时。

> 复核结论（2026-10-14）：现有材料足以说明「某条 socket 已关闭而应用仍向其发送请求」及「连接类错误识别与批次恢复能力不足」，但**不能证明 Wi-Fi 息屏省电就是本次断连的直接原因**，应保留为待验证假设，不写成已确认根因。

### 4.3 方案

**方案一（必做）：传输期间保活**——批次运行期间在原生侧持有 `WifiManager.WifiLock(WIFI_MODE_FULL_HIGH_PERF)` + `PowerManager.PARTIAL_WAKE_LOCK`，批次结束释放。改动点：
- [MainActivity.kt](file:///e:/Code/Projects/MiPix/app/android/app/src/main/kotlin/com/chesereri/mipix/MainActivity.kt)：新增 MethodChannel（`mipix/keepalive`），提供 `acquire`/`release`。
- [AndroidManifest.xml](file:///e:/Code/Projects/MiPix/app/android/app/src/main/AndroidManifest.xml)：新增 `WAKE_LOCK`、`ACCESS_WIFI_STATE`、`ACCESS_NETWORK_STATE` 权限。
- [transfer_provider.dart](file:///e:/Code/Projects/MiPix/app/lib/providers/transfer_provider.dart)：批次进入 `acquire`、`finally` 中 `release`。
- 不需要前台服务/通知栏/MIUI「省电无限制」。诚实说明：「绝对不中断」无工程保证（路由器/NAS 侧也可能主动断开），但能消除「一息屏就断」主因。

**方案二（必做）：断线后在开屏/网络恢复时自动 SMB 重连续传**
1. 给 `createConnection` 补 `onDisconnect` 回调（与缓存连接一致），连接一死立即标失效。
2. `isConnectionError` 纳入 socket 关闭类错误（`streamsink is closed`、`socket is closed` 等**明确本地 socket 关闭错误**，不要以过宽的 `bad state` 匹配所有程序错误），并阻止此类异常逃逸为 `Unhandled Exception`。
3. 通过 MethodChannel 注册 `ConnectivityManager.NetworkCallback` + `ACTION_USER_PRESENT`/亮屏广播，回传 Dart；批次置 `paused`（暂停而非失败，**保留剩余队列**），事件到达后重建连接池续传。
4. 兜底：长时间无法恢复则整批判失败，保留 `retryFailedUploads` 手动续传入口。

**方案三（加固）：失败快速收敛**——连续 N 次连接类失败即中止整批（或转 paused），避免每文件各自空转 15–30 秒；与方案二共用同一状态机。

> 幂等性：大文件分片上传采用「按字节区间覆盖写 `.mipixtmp` → 全部写完 rename」，断线后重传同一文件是幂等的，不会留下半截"锁死"文件。但该结论需覆盖不同失败时机（旧分片仍在运行、超时但服务端仍处理、清理临时文件失败、重连与重试交叠）验证。

### 4.4 保活锁引用计数修复（已实施）

**问题（静态审查第 5 项 + 历史教训）**：全局布尔值标记持有状态，会导致重叠备份批次互相顶掉锁 → 息屏后无锁上传。且并发申请时（第一次原生申请未完成），第二个调用递增计数后立即返回；若第一次申请失败，异常处理只减一次计数，计数仍可能 > 0 但原生锁实际未持有。

**方案**：保活锁改为**引用计数**——仅在计数 **0→1** 时申请原生锁、**1→0** 时释放；串行化原生申请与释放，或记录原生锁是否确实获取成功，确保仍在运行的批次可重新申请。

**结果**：14 项应用侧测试全部通过；真机验证显示多批次备份场景下保活锁可连续持有至对应批次结束，息屏期间锁正常生效，无 `StreamSink is closed` 或未处理异常，所有任务完成无失败。（当前设备无待备份照片，5–10 分钟息屏长批次验证需用户拍摄新照片或授权 adb 推送测试文件触发。）

### 4.5 风险与待确认

- 本机当时安装的 APK 堆栈行号与当前工作区源码**对不上**（装的不是当前源码），修复后必须重新构建安装才能验证。
- 需新增 3 个权限，需用户确认；重装若签名不同会**清空应用数据**（历史教训），需提前备份配置。
- Android 14 起 `WIFI_MODE_FULL_HIGH_PERF` 已弃用并被映射为 low-latency 模式，可能增加耗电、硬件不支持时可能无效，须在目标机型实测。
- 若产品目标是「启动备份后切后台/息屏仍持续传输」，需评估前台服务及常驻通知（当前 `targetSdk = 35`，需遵循对应前台服务类型与限制）；若允许息屏暂停，则实现明确暂停/恢复 + 安全续传。**无论哪种模式，都要保证旧 worker 退出后才恢复队列。**

## 8. 关键工程约束速查

- **64 KiB 硬上限**：Samba 4.19 单次写入上限 64 KiB，客户端 `_uploadChunkSize = 64936`，加大触发 `STATUS_INVALID_PARAMETER`。
- **临时文件 + 原子改名**：上传一律写 `.mipixtmp`，全部写完再 rename；失败不暴露半成品；断线重传幂等。
- **签名**：SMB2.1 用 `package:crypto` HMAC-SHA256（已优化），SMB3 用 pointycastle AES-CMAC；签名语义（清签名域 → 置 `SMB2_FLAGS_SIGNED` → 计算 MAC → 前 16 字节写入）不变。
- **`maxWriteSize`**：smb_connect 协商返回的是客户端侧计算值，不代表服务端真实能力，不可直接作为分块依据。
- **缩略图三级缓存**：内存 → 磁盘 → 远端 EXIF 内嵌缩略图；7 天 TTL + 上限淘汰。
- **保活锁引用计数**：仅 0→1 申请、1→0 释放，避免重叠批次互相顶掉锁。
- **增量备份 fail-closed**：清单读取失败不写入该目录任何文件，并给可重试原因与 UI 文案。
- **状态管理**：flutter_riverpod，按 app/photo/album/smb/transfer 模块划分 provider；相册分组遵循「系统/我的/更多」三段结构。
- **媒体库**：photo_manager 对接 Android MediaStore；图片查看器用自研 `_ZoomableImage` 避免与 PageView 手势冲突。
- **FUSE 云隐（GPS）**：Android 10+ 缺 `ACCESS_MEDIA_LOCATION` 时，读照片会把 EXIF 位置信息数值区间置 0 且**文件长度不变**；必须在读取前持有该权限。裸路径读取无法用 `setRequireOriginal()`。
- **上传后落盘校验**：rename 之前做一次远端 stat，**远端临时文件长度 == 本地源文件长度**才改名；不等则删临时文件并报错（近零成本）。早期版本的「完整回读算 SHA-256」已于 2026-10-17 移除（见第 13 节）。
- **拍摄时间回写**：上传成功后用拍摄时间 `setFileTime` 回写远端文件时间，否则备份端时间会变成备份时刻。
- **`lastModified` 单位**：SMB 返回的时间戳已是毫秒，转 `DateTime` 时不要再乘 1000。

## 9. 备份端照片时间戳与手机相册不符

> 时间：2026-10-15　状态：已修复并真机验证

### 9.1 现象

备份到 NAS 的相机相册照片，时间戳与手机相册里的拍摄时间不一致：部分显示成备份时刻，部分在文件管理器里显示成离谱年份。

### 9.2 根因（两处）

1. **上传不携带拍摄时间**：`smb_connect` 没有 `setFileTime` 能力，文件写完后远端时间由 Samba 设为「服务端写入时刻」，于是备份端时间 = 备份时间。
2. **读取侧多乘了 1000**：SMB 相册浏览用 `DateTime.fromMillisecondsSinceEpoch(file.lastModified * 1000)`，而该值本就是毫秒，结果被放大 1000 倍，日期显示成公元数万年。

### 9.3 方案

- **抽象层**：`SmbConnect.setFileTime(file, {lastWriteTime, createTime, lastAccessTime, changeTime})`，默认实现抛 `UnsupportedError`。
- **SMB2 实现**：`SMB2 SET_INFO` + `FILE_BASIC_INFO`，以 `FILE_OPEN` + `FILE_WRITE_ATTRIBUTES` 打开；`attributes` 传 0（`FILE_BASIC_INFORMATION` 语义为不修改文件属性）；`createTime` 默认沿用 `lastWriteTime`，`lastAccessTime`/`changeTime` 传 0 表示不修改；非 `NT_STATUS_OK` 抛 `SmbException`。
- **主流程**：上传成功且改名完成后调用 `_applySourceTime` 回写；回写失败只记日志，不影响备份结果。
- **拍摄时间来源**：`PhotoService.captureTimesForPaths`（按 `relativePath` 规范化建索引，命中 EXIF 拍摄时间，未命中回退 `File.lastModified()`）；`transfer_provider` 创建任务时带上 `captureTime`，上传时作为 `sourceTime` 传入。
- **读取侧**：删掉多余的 `* 1000`。

### 9.4 代码位置

| 位置 | 说明 |
|---|---|
| `app/packages/smb_connect/lib/src/connect/smb_connect.dart` | 抽象 `setFileTime` |
| `app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_connect.dart` | SMB2 `setFileTime` 实现 |
| `app/packages/smb_connect/test/file_basic_info_test.dart` | 新增：`FILE_BASIC_INFO` 编解码单测 |
| `app/lib/services/smb_service.dart` | `_applySourceTime`（两条上传路径各调用一次）；修正 `* 1000` |
| `app/lib/providers/transfer_provider.dart` | `_PendingUpload.captureTime` → `sourceTime` |
| `app/lib/services/photo_service.dart` | `captureTimesForPaths` |

### 9.5 结果与验证（真机）

覆盖安装到 Redmi K20 Pro（Android 11）后重新备份，备份端照片时间与手机相册拍摄时间**完全一致**，应用配置无丢失。新增 `file_basic_info_test.dart` 单测防止该逻辑退化。

## 10. 备份端照片 GPS 位置信息丢失（Android FUSE 云隐）

> 时间：2026-10-15　状态：读侧已修复并真机验证；历史副本策略待决策

### 10.1 现象

备份到 NAS 的照片，EXIF 里的 GPS 为空（经纬度全 0）；而手机相册里同一张照片的 GPS 正常。时间与画面内容都正确，唯独位置信息丢失。

### 10.2 根因

Android 10 起，应用若缺少 `ACCESS_MEDIA_LOCATION`，`MediaProvider` 的 **FUSE 层**会在应用读取照片时**把 EXIF 中位置信息的数值区间替换为 0**，而**文件长度与其余字节完全不变**。

三个致命后果：

1. `File(...)` 裸路径读取拿到的就是被云隐后的字节；
2. 「同名同大小」去重察觉不到（文件长度没变，内容却已静默改变）；
3. 应用「忠实地」把这些被云隐的字节写进 NAS，GPS 就永久丢了。

> 注：`MediaStore.setRequireOriginal()` 只作用于 **URI 路线**。本工程读取全程是裸路径（自行拼 `/storage/emulated/0/DCIM/Camera/...` 再 `File(...).open()`），没有 URI，故该 API 不适用；`photo_manager` 的 `originFile` 在 Android 11 上返回的也是同一路径。

### 10.3 取证（只读实测，2026-10-15）

样本 `/storage/emulated/0/DCIM/Camera/IMG_20260725_180930.jpg`（3,239,398 B，含 GPS）：

| 读取方 / 状态 | SHA-256 | EXIF GPS |
|---|---|---|
| 原件（PC 上小米云下载副本） | `631dbdc1582c6cc5b04b943d70fb74e9bd3bc7e8d0c24408fb6c194aca127780` | 40.286106, 122.15085 |
| 设备 shell（`sha256sum`） | 同上 | — |
| 应用 · **未授予**权限 | `c2cbe33af70b2cfab97f7758694d4534c1b52f7a57aeffa73c0ed16295fffec6` | 0.0, 0.0 |
| 应用 · **已授予**权限 | `631dbdc1…7780`（= 原件） | 40.286106, 122.15085 |

结论：**Android 11 上，持有 `ACCESS_MEDIA_LOCATION` 后裸路径读取即返回未云隐的原件字节**。取证用临时只读探针完成，全程未写 NAS；探针已删除。

### 10.4 方案（全部已实施）

1. **读侧前置授权**：读取前申请 `ACCESS_MEDIA_LOCATION`（`MainActivity.ensureMediaLocation`，通道 `mipix/permission`），`AndroidManifest` 声明该权限。
2. **上传后落盘校验（当前实现）**：`smb_service` 的 `_verifyUploadedTemp` 在 rename 之前做一次远端 stat，比对**远端临时文件长度 == 本地源文件长度**（成本近似为零），不等即删临时文件并抛错，正式文件名上始终保留旧文件（fail-closed）。两条上传路径（单连接 / 并行分块）都在 rename 之前调用。
   > 变更（2026-10-17）：早期版本此处是「完整回读远端临时文件算 SHA-256 再比对」（`_hashLocalFile` / `_hashRemoteVia` / `range_hash_sequencer`），因大文件上耗时数分钟且失败率高（详见第 13 节），已移除并改为上述长度比对。长度比对查不出「长度不变、内容静默变化」，但该类损耗发生在**手机端读取阶段**（见 10.2），与上传落盘无关，已由读侧授权修复覆盖。
3. **不完整备份可见化**：`PhotoService.mediaLocationGranted`（`ValueNotifier`）→ `mediaLocationGrantedProvider` → 传输页顶部提示条 + 「去授权」按钮；授权被拒时明确告知「本次备份不含位置信息」，而不是只打日志。

### 10.5 验证（真机，2026-10-15）

用修复后的读取路径按正式备份流程上传同一张样本，NAS 端独立核对：

## 11. 界面静止仍满帧出帧的空转（缩略图误把无限循环 GIF 当动图解码）

### 11.1 现象

- 冷启动后停在照片时间轴（界面静止、无可见动画、无传输任务），进程 CPU 长期 ≈**86%
  单核**，60Hz 面板下持续 ≈**47fps** 出帧。
- 备份期间叠加这份开销后，表现为长时间无日志、主 isolate 满载——与用户感知的「传输卡住」一致。

### 11.2 根因

`Image.file` 对 `codec.frameCount > 1` 的图片返回 `MultiFrameImageStreamCompleter`
（`painting/image_provider.dart` → `FileImage.loadImage`），其 `_handleAppFrame`
（`painting/image_stream.dart`）会在下一帧时刻通过
`scheduleFrameCallback` → `scheduleFrame` **自续调度**；`repetitionCount == -1`
（无限循环动图）时永不终止。只要还存在 listener，界面静止也会满帧出帧。

缩略图（照片网格 + 相册封面）用 `Image.file(path, cacheWidth: 400)` **直接解码原图文件**，
于是相册里两个无限循环 GIF 的缩略图也走多帧解码路径。

次要放大：系统无障碍（a11y，`enabled_accessibility_services` 含 MIUI 安全中心服务）开启时，
每帧会额外遍历一遍语义树。此项非出帧驱动，仅为伴生开销。

### 11.3 取证（profile 构建 + VM Service，2026-10-16，真机 Redmi K20 Pro / Android 11）

## 13. GPS 修复后传输耗时增加与校验优化建议

> 时间：2026-10-16 起　状态：**本节的「上传后回读 SHA-256 校验」相关方案（P2/P3）已于 2026-10-17 整体移除**，改为「远端临时文件长度 == 本地源文件长度」的近零成本比对；P0/P1（阶段文案、阶段日志、队列清理与排序）保留。下方 13.1~13.10 保留了当时的分析与实施记录，凡涉及回读哈希处均已标注【已移除】。
>
> 范围：解释 GPS 数据修复后「全部备份」体感变慢的原因，区分权限/元数据处理与校验成本，并记录最终决策（去除回读、只留长度比对）及其取舍。

### 13.1 结论摘要

性能明显下降的主要原因不是 GPS 字节或 GPS 权限本身，而是 GPS 修复同期加入了「上传后完整回读远端临时文件并计算 SHA-256」：文件上传完成后，必须先从 NAS 再读回完整内容，与本地 SHA-256 比较，匹配后才能把 `.mipixtmp` 改名为正式文件。大文件的这段时间上行流量接近零，但 SMB 下行仍在传输，因此 UI 容易被理解为卡住。**该回读校验已于 2026-10-17 整体移除**，改为近零成本的「远端临时文件长度 == 本地源文件长度」比对（一次远端 stat），性能负担基本消失。

GPS 修复仍然必要：Android 10+ 的 MediaProvider/FUSE 在缺少 `ACCESS_MEDIA_LOCATION` 时可能云隐 EXIF GPS，长度不变但内容改变。授权后上传真实原始字节，修复了数据正确性。**这类「长度不变、内容静默变化」的损耗发生在手机端读取阶段**，由读侧授权修复覆盖，与上传落盘校验无关；因此去除回读哈希不会削弱 GPS 完整性保证，长度比对仍可在 rename 前拦住「服务端只写入部分字节、临时文件变短」这类失败。

### 13.2 当前代码路径（静态核对）

1. `PhotoService.ensurePermission()` 在媒体访问授权成功/受限时调用 `ensureMediaLocationAccess()`。该权限让后续文件读取能够保留 GPS；没有证据表明权限获取本身会降低持续 SMB 吞吐。
2. `TransferNotifier._backupPhotosImpl()` 在备份开始时调用 `captureTimesForPaths()` 查找拍摄时间。该方法会分页扫描媒体库（每页最多 200 项）直到找到全部目标或扫描结束；大批量任务可能有独立的启动延迟，但不是大视频上传结束后数分钟低上行的原因。
3. 大文件由 `SmbService.uploadFileParallel()` 按多个字节区间、多条连接写入同一个临时文件。小文件由 worker 连接池调用 `uploadFileVia()`。
4. 两条上传路径都会调用 `_verifyUploadedTemp()`：只做一次远端 stat，比对**远端临时文件长度 == 本地源文件长度**；长度不符（含远端不存在 / stat 失败而返回 -1）即失败关闭——删临时文件 + 抛错，不执行 rename。
5. `PhotoService.hashFile()`（用于「同名同大小」冲突比较，见第 3 节）仍使用 `Isolate.run()`；它属于**上传前的冲突判定**路径，与上传后校验无关，未受影响。
6. 上传分片连接在 `uploadFileParallel()` 校验前已经关闭（每个分片写完自己的区间后自行关闭句柄与连接，见 13.12）；长度比对使用独立的 `setup` 连接做一次远端 stat。

### 13.3 为什么体感会下降

> 【历史分析】以下解释对应**已移除**的上传后回读 SHA-256 校验；仅作成本归因记录。当前实现不再有该阶段。

- **额外远端 I/O 是主因**：上传 1.4 GB 后，校验又要从 NAS 读约 1.4 GB。报告中的真机样本上传约 70 秒，回读校验约 298 秒；此时 TX 接近零、RX 持续增长，与回读校验路径一致。
- **远端读并发度低于写入**：大文件上传按多连接分片并行，上传后回读当前是单连接顺序读。读缓冲从 4095 调到 64936 已提高单连接吞吐，但无法消除单连接请求/响应吞吐上限。
- **本地文件也被再次读取**：`_hashLocalFile()` 在上传后再扫一遍源文件。它增加本地 I/O 和 CPU，但相比远端完整回读通常不是大文件总耗时的主项；其是否影响 UI 响应应以真机 profile 测量。
- **队列展示会放大等待感**：历史失败项排在新任务前面时，实际运行任务和校验进度不容易看到。该点影响可观察性，不改变传输耗时。
- **其他可测启动成本**：`captureTimesForPaths()` 的媒体库扫描、远端清单读取、同名同大小冲突比较（`hashRemoteFile()` + 本地哈希）发生在写入前，需与上传后校验分开计时，避免把不同阶段混为一谈。

### 13.4 关于「所有文件上传完后统一计算 SHA-256」

> 【已作废】该方案的目标是优化**已移除**的回读校验，随回读一同作废，保留仅作决策留痕。当前实现为「rename 前做一次远端长度比对」。

该方案要区分本地摘要和远端摘要：

- **统一延后远端回读不会减少总网络字节或校验工作量**：仍需从 NAS 读取每个文件的全部内容。它只把每文件上传后的等待移动到整批上传结束之后，整批正式完成时间不会因此必然缩短。
- **延后会推迟所有文件的 rename/成功状态**：若继续保持「校验通过后才改名」，批次中的文件在统一校验结束前都只能保留为临时文件。若上传后先 rename、之后再验，则验失败时正式路径已经暴露错误内容，失去当前原子完整性语义，不建议这样做。
- **批次中断的恢复成本变大**：更多临时文件会在最终校验前等待；应用退出、断网或存储空间不足时需要额外持久化校验队列与恢复状态。
- **可以减少上传后的本地重读**：本地 SHA-256 可在上传数据流经过时累计，或与上传并行计算；但普通 SHA-256 必须按文件字节顺序更新。多分片各自得到的摘要不能直接拼接成整文件 SHA-256。更简单的并行做法是让单独的本地 isolate 计算完整文件摘要并与上传重叠，但磁盘读取总量未减少。
- **上传流中的本地摘要不等于远端校验**：它只能记录客户端读出/发送的数据，不能证明服务端最终落盘字节相同。若要检出 NAS 写入错乱、短写或存储侧静默损坏，仍需读回远端或采用服务端可信校验机制。

结论：不建议仅把远端校验改成批次末尾统一计算。优先在不改变 fail-closed 与先验后改名语义的前提下，降低单文件校验时长，并减少/重叠本地摘要读取。

### 13.5 建议的修改顺序

> 【部分作废】P0/P1 已实施并保留；**P2（本地摘要与上传重叠）与 P3（远端多连接区间回读）随回读校验一并移除，不再实施**（见 13.8 / 13.12）。下方 P2/P3 条目仅作当时的规划留痕。

#### P0：把阶段和耗时展示清楚（低风险）

- 任务阶段清楚区分「准备/冲突比对」「上传」「NAS 回读校验」「改名与时间戳回写」。
- 校验阶段显示已读/总量、当前读取速度和阶段耗时；上传阶段与校验阶段使用不同文案。不要只把两段合成一个 0–100% 进度，让大文件校验期间看起来像上传停滞。
- 增加阶段级耗时日志：媒体库拍摄时间查询、远端清单、冲突哈希、上传、本地摘要、远端摘要、rename、时间回写分别计时。每项应带远端路径/任务 ID、字节数和有效吞吐，避免记录密码等敏感配置。

#### P1：修复队列可见性（低风险）

- `backupPhotos()` 新建任务前，按 `serverId + localPath` 精确移除该文件的历史失败上传记录，避免新批次重复项被旧记录淹没；不要删除其他服务器或其他路径的失败项。
- 队列排序建议为运行中、等待中、近期终态、较早终态；或将终态历史折叠。保证当前批次运行项一打开即可见。
- 现有 `retryFailedUploads()` 已在重试前移除旧失败记录，可抽出共用的按目标身份清理逻辑，避免「重试失败」与「全部备份」行为分叉。

#### P2：重叠或消除本地二次读取（中风险）

- 先测 `_hashLocalFile()` 是否在主 isolate 造成明显事件循环抖动。若有，使用 isolate 对本地文件做流式哈希，并与上传并行；SMB 连接操作仍留在创建它的 isolate。
- 后续可评估上传与本地 SHA-256 共用同一份本地数据流。小文件 worker 上传可自然按块顺序更新摘要；大文件分片则需单独的有序哈希流，不能把各片段 SHA-256 直接拼接。若实现复杂或争用本地存储 I/O，采用并行本地哈希方案即可。
- 任一模式都需核对哈希期间文件长度/修改时间或内容版本，避免本地文件在上传与哈希之间变化而产生错误结论。

#### P3：优化远端校验吞吐（中高风险，需原型及真机验证）

- 对大文件实现多连接区间读取：每连接读取明确的 `[start, end)` 范围，读取块带 offset/序号，按文件顺序进入单个 SHA-256 chunked sink。
- 使用固定大小块和有界重排缓冲；禁止把每个大分片整体缓存后等待前序分片，否则内存随文件大小增长。
- 每段读取需验证起止偏移、累计字节数、远端初始/结束大小；任一连接失败、短读、超时或摘要不完整均 fail-closed，删除/保留临时文件按既有清理策略处理，绝不 rename。
- 为并发度设置可配置上限，按 NAS 能力与 Wi-Fi 实测选择；连接建立、认证和服务端限流可能使高并发无收益。现有上传连接已关闭，不能直接复用，除非重构连接生命周期并实证复用安全。
- 另行评估是否存在可信 SMB 服务端校验接口；只有服务端计算的是实际远端文件字节摘要且响应受信任时，才能替代客户端完整回读。不能假定普通 SMB 写成功响应提供内容哈希。

### 13.6 验收与回归要求

优化前后使用同一设备、NAS、Wi-Fi、文件和并发配置，分别记录：

| 指标 | 记录方式 |
|---|---|
| 媒体库与远端清单准备耗时 | 阶段墙钟计时 |
| 上传吞吐 | 本地读取/写入字节数 ÷ 上传时间，并与 NAS 文件增长核对 |
| 本地哈希耗时及 CPU | isolate/主 isolate 分别计时与 profile |
| 远端校验耗时、RX 吞吐 | 校验字节数 ÷ 时间，结合网络 RX 计数 |
| 总体完成时间 | 从备份确认至 rename 成功 |
| 完整性 | 本地与 NAS 独立 SHA-256 相同；EXIF GPS 样本仍有效 |
| 故障语义 | 注入短读/断连/超时/哈希不符时不改名，失败可重试 |
| 体验 | 队列当前任务置顶；校验阶段进度持续更新，无误报卡死 |

**判据⑤裁决（更新）**：断网注入下「不 rename + 清理 / 保留临时文件 + 可重试」**已覆盖并满足**（上传段、校验段各一次）。「停 Samba 服务」「服务端短读（少发字节）」两项仍建议在可控 SMB 测试端补充，如实标为未覆盖。

**新发现缺陷 — 重试路径 setup 调用缺卡死超时（真实复现「服务端锁死」）**
- **现象**：注入 B 遗留的僵死 SMB 会话在服务端**持锁**（对应 `MiPixFITest/fit_a.mp4.mipixtmp`——注入 A 写满 703 MB 的孤儿临时文件）。随后重试 `fit_a` 时，`[backup][hash]` 预取正常完成后**再无任何日志**，3+ 分钟不恢复；进程仅剩 2 条空闲 445 连接，无报错、无超时。两次重试均稳定卡住。
- **根因**：上传 / 校验主流程的每次 SMB 调用都有 `_stallTimeout` 看门狗，但**上传前的 setup 阶段**（删除旧 `.mipixtmp` / 建目录 / `createFile` / `setFileTime` 等）**未纳入该超时保护**——服务端因锁未释放而不回 ACK 时，这些 await 会被无限挂住（与「WiFi 静默断开导致 flush 挂死」同类），表现为「传输卡死且无日志」。
- **影响**：`.mipixtmp` 是防脏数据的正确机制；但当服务端残留锁未释放时，会**阻塞后续重试**，需人工重启 Samba 或手动删除孤儿临时文件才能恢复。
- **修复（2026-10-17 已实施）**：把 setup 阶段所有可被「服务端残留锁不回 ACK」挂住的 SMB 调用统一包进 `_guard`（`_stallTimeout`，30s）看门狗：
  - [createDirectoryVia](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart#L1423) 的 `createFolder`；
  - `uploadFileParallel` 单连接回落与分片准备阶段的 `createConnection`（含续传回调内的重建）；
  - `_applySourceTime` 的 `setFileTime`；
  - 原有的 `_deleteRemoteIfExists` / `createFile` / `file` / `rename` / `writeFrom` / `remote.close` 早已纳入。
  超时统一按连接类错误（`TimeoutException`，见 `isConnectionError`）抛出 → fail-closed：不 rename、清理临时文件、任务落 `failed` 供「重试失败」续传，**不再无限挂死**。`transfer_provider` 的 `openConnection` 另有 20s 建连超时兜底。
  > 未实施（评估后认为当前不必）：批次启动前对同名 `.mipixtmp` 的「带超时清理探测 + 锁占用提示」。当前实现超时即 fail-closed 并显式落失败态，已消除卡死这一核心症状。
- **当前处置**：待 NAS 侧重启 Samba（或手动删除该孤儿 `.mipixtmp`）后复验 `fit_a` 收尾。

### 13.12 最终方案（2026-10-17）：去除回读、只留长度比对

**决策**：上传后不再回读整份内容重算 SHA-256，改为 rename 前一次远端 stat 的**长度比对**。理由：全量回读在大文件上耗时数分钟、失败率高，而它查不出「长度不变、内容静默变化」；这类损耗实际发生在**手机端读取阶段**（GPS 云隐，见第 10 节），已由读侧 `ACCESS_MEDIA_LOCATION` 授权修复覆盖，与上传落盘无关。

**代码变更**
- **删除**：`range_hash_sequencer.dart`、`decideVerify` / `VerifyOutcome`、`_hashLocalFile`、`_hashRemoteVia`、`_hashRemoteRangeVia`、`rangeReadbackConcurrency`、`rangeReadbackRangeBytes`，以及 P2 的摘要预取与来源稳定锚点参数；`TransferPhase.localHash` / `verifying` 两个阶段。
- **保留**：`_verifyUploadedTemp`（改为长度比对：`File(localPath).lengthSync()` 与 `_remoteFileSize` 比较，不等即删临时文件 + 抛错）、`.mipixtmp` 原子发布（写完才 rename）、rename 前 fail-closed、`setFileTime` 拍摄时间回写。
- `TransferPhase` 收缩为 **preparing / uploading / finalizing**。

**大文件并行上传断链续传（同期修复）**
- **现象**：Win7/SMB2 服务端在写入过程中偶发长时间不响应；库内 `SmbTransport.waitResponseTimeout`（3 秒）一到即重发同一 MID 请求，服务端随即断开该连接，客户端后续写入命中已关闭 socket，抛 `Bad state: StreamSink is closed`。并发=1 与大文件分片都命中，证明与分片并发无关，是服务端行为。
- **修复**：[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart) 的 `_writeRange` 每轮（首传 / 重连续传）重建连接、重开远端句柄、定位到**最后一个已确认写入的偏移**续写，不再让整个文件从头重来；重连上限 `_shardMaxReconnects = 20`（详见 [_shardMaxReconnects](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart#L1336-L1347)）。
- **实测**（Win7 测试服务器，800 MiB）：4 分片 + 续传完成、0 失败分片、10 次重连、约 59 秒；单连接亦完成（1 次重连）。结论：只需应用层续传，**不改库、不覆盖 `waitResponseTimeout`**（3 秒反而更快——能更早放弃卡住的请求并续传）。
- **单连接路径（`uploadFileVia`）同样加续传**：把原先的 `openWrite`（IOSink）改为随机定位写（`open` + `setPosition` + `writeFrom`），rename 前先探测远端临时文件：长度落在 `(0, total)` 之间即从该长度续写，否则删掉重写。断链时若有 `reconnect` 回调则在本函数内重建连接续传（并发=1 的大文件由 `uploadFileParallel` 提供回调并管理新建连接；小文件 worker 池由 `transfer_provider` 提供回调，关闭并重建该槽位连接）。这样「并发数=1」的大文件不再每次重试都从 0 重来。

**验证**：`dart analyze lib/services/smb_service.dart` 无新增 error（仅存量 warning）；`flutter test test/transfer_recovery_test.dart` **43 项全通过**。

**根因**：客户端侧网络瞬断（Wi-Fi 重关联 / 网卡漫游）。判定依据：同一瞬间多个已建立 socket 报 `errno 103`，紧接着新建连接全部失败，而服务端日志显示此刻仍在正常接客 —— 这是 Android 网卡 down/re-associate 时 abort 全部 socket 的典型特征。

**应用侧真正的问题（本次修复）**：

1. **`Can't connect` 未被识别为连接类错误** —— vendored `smb_connect` 建连失败抛的是**裸字符串** `"Can't connect to <host>"`（既不是 `SocketException`，也不含 NT 状态名），而 `SmbService.isConnectionError` 仅靠消息关键字匹配，没有覆盖它 → 判成「非连接错误」→ **一次抖动就把文件判死**，且还会把 `UploadFailureGuard` 的连续失败计数**清零**（链路明明已断，却永远达不到 5 次停批阈值）。
2. **重连失败即立即收敛** —— 原逻辑 `if (!retryable || reconnectFailed) return e;`，Wi-Fi 漫游的那几秒里重建连接必然失败，于是第 1 次就终结，**没有给网络恢复留任何窗口**。
3. **重试之间没有退避** —— 即使能重试，也会在几十毫秒内连打 3 次，既等不到链路恢复，又可能把服务端连接闸门顶穿。

**修复**（[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart#L1375-L1385)、[transfer_provider.dart](file:///e:/Code/Projects/MiPix/app/lib/providers/transfer_provider.dart#L141-L209)）：

- `isConnectionError` 增加建连 / 链路类判定：`can't connect`、`cant connect`、`cannot connect`、`failed to connect`、`connection refused`、`no route to host`。
- `uploadWithRetry` 新增 `backoff` 参数（默认阶梯 **1s → 2s → 4s，8s 封顶**），在每次重试（含重建连接）**之前**等待，等效于「等网络回来再继续」。
- 重连失败**不再立即收敛**，改为继续消耗重试预算；且**不再把 reconnectError 计入 guard**（同一失败回合的上传失败与重连失败是同一件事的两面，重复计数会让停批阈值提前一倍触发，一次短抖动就可能误判整批剩余文件）。
- 失败回合内的日志 `reconnectFailed` 语义保留（仍如实记录 `reconnect=failed`），便于区分「连不上」与「上传中途断」。
- **未加网络状态插件**：`connectivity_plus` 需要新增依赖与权限，但上述退避已覆盖秒级抖动（本次故障窗口约 60s，若持续更久仍会 fail-closed 并留下「重试失败」入口，语义不变）。如后续需要「断网即暂停、恢复即续跑」的强语义，再引入连接状态订阅。

**验证**：新增/更新单测覆盖「建连失败裸字符串识别」「重连失败不立即收敛」「瞬断后链路恢复最终成功」；`flutter test` **51 项全绿**，`flutter analyze lib test` → **No issues found**。

## 15. SMB 远端视频在线预览（本地回环 HTTP 代理 + 内置播放器）

### 15.1 现象与需求

SMB 相册里的视频只有一个占位卡片，点开后无法播放。用户要求：

- 在应用内直接在线播放远端视频，**不是先下载再看**；
- 播放界面样式与小米相册一致（顶部信息栏、浮动控制胶囊、底部操作栏）；
- 服务器端**不需要安装任何额外服务**（NAS 上不能装插件/转码服务）；
- 大文件（例如 10 GB）不能因为播放而在手机本地留下整份副本。

### 15.2 根因与备选方案

Android 端 `video_player` 底层是 ExoPlayer，它只接受 `http/https/file/content` 等 URI，**无法直接读 SMB**。可选路线：

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 本地回环 HTTP 代理 | 应用内起一个只听 `127.0.0.1` 的 HTTP 服务，把播放器的 `Range` 请求翻译成 SMB 区间读取 | **采纳** |
| B. 先整文件下载再播放 | 下载到缓存目录后 `VideoPlayerController.file` 播放 | 否决：10 GB 级视频会占满本地空间，且起播等待时间不可接受 |
| C. 自研 SMB 播放器 | 自己解析容器 + 软解 | 否决：工作量与风险远超收益，且无法复用系统硬解 |

方案 A 的关键优势：**服务器端零安装、播放器走标准 HTTP 语义、按需读取字节区间**。

### 15.3 实现：`RemoteVideoProxy`

代码位置：[remote_video_proxy.dart](file:///e:/Code/Projects/MiPix/app/lib/services/remote_video_proxy.dart)

- 单例 `RemoteVideoProxy.instance`，首次 `register()` 时懒启动 `HttpServer.bind(InternetAddress.loopbackIPv4, 0, shared: true)`（端口由系统分配，仅监听回环地址）。
- `register(config, remotePath, name)` 生成 **12 字节 `Random.secure()` 随机 token**（hex），登记会话并返回：
  - `url`：`http://127.0.0.1:<port>/v/<token>/<urlencode(name)>`
  - `token`：播放页销毁时 `unregister()` 用。
  路径里只放 token 与文件名，真实共享目录/凭据不进入 URL。
- 路由 `GET` / `HEAD /v/<token>/<fileName>`；token 不存在回 `410 Gone`，避免播放器对已结束会话反复重试。
- `Range` 解析支持 `bytes=a-b`、`bytes=a-`、`bytes=-N` 三种写法：
  - 合法区间回 **206** + `Content-Range: bytes a-b/total` + `Accept-Ranges: bytes`；
  - 无 `Range` 回 **200** 全量；
  - 非法区间回 **416** + `Content-Range: bytes */total`（播放器据此重新协商）。
- 文件大小在 `_VideoSession.size` 内缓存：一次播放会话内长度不会变，避免每个 Range 请求都 stat 一次。
- `response.bufferOutput = false` + 每个分块 `await response.flush()`：形成背压，SMB 读一块、HTTP 发一块，内存里始终只有 64 KiB 级缓冲。
- 监听 `response.done`：播放器退出或拖动进度条导致连接断开时置 `clientGone`，停止继续读 SMB，底层流随之取消。
- `Content-Type` 按扩展名映射（mp4/m4v、mov、mkv、webm、ts、flv、3gp、avi、wmv），未知回 `application/octet-stream`；带 `Cache-Control: no-store`，防止中间层缓存整段视频。

### 15.4 SMB 侧的区间读取

代码位置：[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart)

- `remoteFileSize(config, remotePath)`：独立建连读 `file.size`，最多 2 次重试。
- `openRemoteVideoRange(config, remotePath, start, endExclusive)`：以 `async*` 返回字节流。
  - **独立连接**而不是共享连接池：视频是长时间顺序读取，复用池连接会与缩略图/列表请求互相排队，直接表现为播放卡顿；同时也不会因播放占住池内连接而拖慢相册浏览。
  - `end` 按真实文件长度 clamp；`start` 越界直接返回空流。
  - `stream.timeout(_stallTimeout)`：复用现有 30 s 读写停滞超时，网络假死时不会永久挂住。
  - `finally` 关闭连接：消费者取消订阅（播放器断开、拖动）时释放远端会话。
- 底层 `smbOpenRead` 的读循环改为 `try { ... } finally { await smbCloseFile(...) }`（见第 19.6 节），保证取消订阅时文件句柄也被关闭。

### 15.5 播放器与界面

代码位置：[photo_viewer_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/photo_viewer_screen.dart)

- `_RemoteVideoPlayer` 通过 `RemoteVideoProxy.instance.register()` 拿到本地 URL，再 `VideoPlayerController.networkUrl(handle.url)`；`_LocalVideoPlayer` 仍用 `VideoPlayerController.file`。
- 界面按小米相册拆分：
  - `_VideoTopBar`：白底、返回、日期、「时间 · N/24」、锁定按钮；
  - `_VideoControls`：浮动胶囊，收起态为「播放/暂停 + 进度条 + 静音」，拖动时展开为「mm:ss.CC / 总时长」+ 圆形滑块 + 「上滑进入精细调节」提示；
  - `_BottomActionBar`：白底五键（分享、备份/下载、删除、信息等）；
  - 播放失败时展示错误态与重试，不把异常抛到页面外。
- 远端「下载」用 `_downloadRemote`：按流写入临时文件，再 `PhotoManager.editor.saveVideo(tempFile, relativePath: 'Movies/MiPix')`，随后删除临时文件——不经过内存整份缓存。

### 15.6 为什么不需要「播一段删一段」的流媒体清理

用户追问 10 GB 级视频是否会因播放写入本地。实测与代码核查结论：**不会**。

- `video_player_android 2.10.0` 内部使用 `DefaultHttpDataSource` + `DefaultMediaSourceFactory`，**没有 `SimpleCache` / `CacheDataSource`**，因此 ExoPlayer 只做内存缓冲，不写磁盘。
- 代理侧只把 SMB 分块转发给 socket，不落盘；`CacheService.enforceCacheLimit()` 只统计 `thumb3_cache_`（缩略图）与 `image_cache_`（原图）两类文件，与播放无关。
- 播放路径唯一可能新增的本地数据是：视频缩略图 JPEG（约几十 KB/个）与用户主动点「下载」保存到系统相册的文件。
- 因此 10 GB 视频在线播放对本地存储的影响可忽略，无需额外的分段清理方案；「不做整文件缓存」作为硬约束保留，避免后续改动引入磁盘缓存。

### 15.7 已知限制

- 容器支持取决于 ExoPlayer：mp4/mov/mkv/ts/flv/webm 可播，**AVI / WMV 不支持**（点击后进入错误态）。
- 代理由应用进程托管，进程被杀则播放中断（与所有在线播放器一致）。
- Android 9+ 默认禁止明文 HTTP；应用已在 Manifest 开启 `usesCleartextTraffic="true"`，回环地址才能被播放器访问。

## 16. 远端视频缩略图（原生抽帧 + 内存/磁盘两级缓存）

### 16.1 现象

远端视频在网格里只有播放角标和灰色底，没有画面；本地视频有系统生成的缩略图，远端没有。

### 16.2 根因

- `MediaStore` 只给本地资源提供缩略图，SMB 文件没有对应记录；
- 图片可以「读头部 + `image` 包解码」，视频必须解析容器并解码视频帧，纯 Dart 没有可用且体积可接受的实现；
- 把远端视频整份读下来再抽帧，与「不做整文件缓存」的约束冲突。

### 16.3 方案：原生 `MediaMetadataRetriever` 经代理抽帧

代码位置：[video_thumbnail_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/video_thumbnail_service.dart)、[MainActivity.kt](file:///e:/Code/Projects/MiPix/app/android/app/src/main/kotlin/com/chesereri/mipix/MainActivity.kt)

- 复用第 15 节的回环代理：`MediaMetadataRetriever.setDataSource(url, headers)` 本身支持 `http/https` 且会发 `Range` 请求，因此无需为缩略图单独写 SMB 读取逻辑，也不会整份下载。
- MethodChannel `mipix/video_thumbnail`，方法 `frame`，参数 `{url, timeMs}`：
  - 原生侧放到**后台线程**执行，避免解码阻塞主线程；
  - `getFrameAtTime(timeMs * 1000, OPTION_CLOSEST_SYNC)`：取 1 s 附近的关键帧。选 1 s 是为了跳过片头黑屏，`CLOSEST_SYNC` 只解关键帧、速度远快于精确帧；
  - `Bitmap.compress(JPEG, 82)` 后返回字节；失败（容器不支持、代理读失败）返回 `null`，`finally` 中 `release()` 回收解码器。
- Dart 侧 `_extract()` 在 `finally` 中注销代理会话，避免临时 token 泄漏。

### 16.4 缓存与并发

- **内存缓存**：`Map<String, Uint8List?>`，上限 300 项，超限整体清空。
  - 失败也写入 `null`，用 `knows()` 区分「没查过」与「查过但失败」，避免滚动时对同一个坏文件反复解码。
- **磁盘缓存**：`getTemporaryDirectory()/video_thumbs/<sha1>.jpg`，重装应用前一直有效。
  - 键 = `sha1('$serverId|${item.path}|${item.modifiedAt.millisecondsSinceEpoch}')`，远端文件被替换后修改时间变化，旧封面自动失效。
- **并发闸门**：最多 2 个抽帧任务同时进行，其余排队；`_release()` 在存在等待者时**直接移交名额**（`_active` 保持不变），避免无谓的减一加一。
- 加载顺序：先 `peek()` 同步命中内存 → 再查磁盘 → 最后才排队抽帧；排队期间若同一文件已被其他瓦片完成，直接复用结果。

### 16.5 网格展示

代码位置：[photo_grid_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/photo_grid_screen.dart)

- `_RemoteImage` 改为接收 `MediaItem`（原来只接收 `remotePath`），视频分支走 `_initVideoThumb()`：
  - 先 `VideoThumbnailService.peek/knows` 同步判断，命中直接 `setState` 展示，不产生异步空档；
  - 未命中再读取服务器配置并 `load()`，加载中显示小号 `CircularProgressIndicator`；
  - 有帧后 `Image.memory(bytes, cacheWidth: 400)` 控制解码内存，并居中叠加 `Icons.play_circle_fill`（白色 70% 透明、36 px），与小米相册的视频角标一致。
- 图片路径保持原有的 `SmbService.peekThumbnail` / `_loadingController` 逻辑不变。

### 16.6 验证

- 真机滚动远端视频相册：缩略图逐个出现，加载期间不阻塞其他瓦片。
- 卸载重装后首次进入：命中磁盘缓存，缩略图**秒开**，没有再触发抽帧。

### 16.7 纯视频相册的封面（2026-10-22 追加）

**现象**：只有视频的 SMB 相册（如实测的「所有视频」24 个、「Rokid AI」7 个）在相册列表里只有灰色文件夹占位，而含图片的相册都有封面。注意瓦片本身正常，缺的是**相册卡片封面**。

**根因**：`SmbService._collectAlbums` 里写死了 `coverCandidates = mediaFiles.where(_isImage)`，`_resolveAlbumCover` 只在图片中挑选最新一张。纯视频目录的候选集为空，`coverPath` 直接返回 null。

另一个连带问题：即使把视频路径作为封面返回，`SmbRemoteImage` 也会走 `SmbService.readThumbnail()`，把视频文件按图片解码——必然失败，只能显示 `broken_image`。

**修复**：

- [smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart)：`_resolveAlbumCover` 改为接收全部媒体文件，优先取最新图片，**没有图片时回退到最新视频**并返回其远端路径。
- [smb_image_widget.dart](file:///e:/Code/Projects/MiPix/app/lib/widgets/smb_image_widget.dart)：`SmbRemoteImage` 用 `SmbService.isVideoName()` 判断封面类型；视频封面交给第 16 节的 `VideoThumbnailService` 抽帧，图片仍走原有缩略图链路。封面场景没有修改时间，`MediaItem.modifiedAt` 固定为 epoch 0，换取稳定的缓存键。

## 17. 拖动视频进度条误触发切换上下视频

### 17.1 现象

视频页按住控制胶囊里的进度条左右拖动时，外层 `PageView` 会翻页，切到上/下一个视频；偶尔还会「卡住」——胶囊停在展开态、后续拖动无响应、视频也不再播放。

### 17.2 根因（两个叠加问题）

1. **手势竞技场竞争**：外层是 `PageView` 的 `HorizontalDragGestureRecognizer`，进度条若只是普通 `GestureDetector` 处理 `onHorizontalDragUpdate`，两者同时进入竞技场；`PageView` 的识别器往往先达到 slop 并宣告胜利，于是拖动变成翻页。
2. **拖动过程中元素被重建**：拖动开始时 `_dragging=true`，胶囊从「收起 Row」切换为「展开 Column」。children 结构变化后 Flutter 按位置匹配 Element，进度条整棵子树被销毁重建——旧的手势识别器随之销毁，本次手势剩下的 MOVE/UP 事件全部落到外层 `PageView`；`onEnd` 永远收不到，于是 `_dragging` 卡在 `true`、播放也没有恢复。

### 17.3 方案

代码位置：[photo_viewer_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/photo_viewer_screen.dart)（`_VideoControls`，约 1248–1530 行）

1. **用 `GlobalKey` 固定进度条子树**：
   ```dart
   final GlobalKey _trackKey = GlobalKey();
   ```
   把它挂在进度条的 `LayoutBuilder` 根节点上。Row → Column 切换时，Flutter 通过 GlobalKey 把同一 Element **reparent** 到新父节点，而不是销毁重建；手势识别器与 `_dragStartFraction/_accumulatedDx/_fine` 等状态全部保留，后续 MOVE/UP 继续到达原识别器。
2. **自定义 eager pan 识别器**，在竞技场第一轮直接胜出：
   ```dart
   class _EagerPanGestureRecognizer extends PanGestureRecognizer {
     @override
     void addAllowedPointer(PointerDownEvent event) {
       super.addAllowedPointer(event);
       resolve(GestureDisposition.accepted);
     }
   }
   ```
   手指落在轨道上时立即 accept，`PageView` 的水平拖动无法再抢走这次手势。落点在轨道外时该识别器不参与，翻页行为不受影响。
3. **扩大命中区域**：收起态胶囊的 `Row` 增加 `crossAxisAlignment: CrossAxisAlignment.stretch`，让轨道（含透明命中区）占满胶囊高度，不必精确点中细线才能拖动。
4. **交互细节**：
   - `_beginDrag` 暂停播放并记录起点比例，`_seekTo` 实时 seek 做预览；
   - 上滑超过 2 px 进入精细模式（位移系数 5 倍），便于长视频微调；
   - `onEnd` / `onCancel` 统一走 `_endDrag()`：收起胶囊、恢复播放；
   - 轨道宽度取 `LayoutBuilder` 实测值（收起态约 549 px、展开态约 940 px），比例映射按当前宽度计算。

> 备选方案「拖动时不做结构切换、只改样式」被否决：需求要求胶囊随拖动展开并显示精确时间，结构切换无法避免，因此必须用 GlobalKey 保元素。

## 18. 澎湃 OS 4 本地相册不显示视频（Android 13+ 缺少 READ_MEDIA_VIDEO）

### 18.1 现象

本机共 4 个视频（1 个相机拍摄、3 个录屏）。系统相册能看到，但 MiPix 的「相机」「截屏录屏」「视频」三个相册里都没有视频，只有图片。用户怀疑这两个相册只读图片。

### 18.2 定位

- `adb shell content query --uri content://media/external/video/media` 确认 4 个视频真实存在：
  `DCIM/Camera/VID_20261004_204833.mp4`，以及 `DCIM/ScreenRecorder/Screenrecorder-2026-07-06-*.mp4` ×3。
- 应用侧查询用的是 `photo_manager` 的 `RequestType.common`（图片 + 视频），逻辑上不应过滤视频，因此问题只能在权限层。

### 18.3 根因

`AndroidManifest.xml` 只声明了 `READ_MEDIA_IMAGES`，没有 `READ_MEDIA_VIDEO`。Android 13+ 把这两类权限拆开：缺少视频权限时，`MediaStore` 查询**不会返回任何视频行**（不会报错，只是结果集为空）。因此：

- 相册张数按图片计算，看起来正常；
- 视频既不在原相册里，也不会出现在「视频」聚合相册；
- 现象看起来就像「这两个相册只显示图片」。

`photo_manager` 官方文档也明确要求两张权限同时声明。

### 18.4 修复

代码位置：[AndroidManifest.xml](file:///e:/Code/Projects/MiPix/app/android/app/src/main/AndroidManifest.xml)

```xml
<uses-permission android:name="android.permission.READ_MEDIA_IMAGES"/>
<uses-permission android:name="android.permission.READ_MEDIA_VIDEO"/>
```

并补充注释说明「两者必须同时声明，否则查询看不到任何视频」。应用首次启动时 `PhotoManager.requestPermissionExtend()` 会一并申请两项。

### 18.5 验证

| 范围 | 修复前 | 修复后 |
|---|---:|---:|
| 全部照片（含视频） | 400 | 404 |
| 相机相册 | 135 | 136 |
| 视频相册 | 0 | 4 |
| 截屏录屏相册 | 30 | 33 |

真机确认：相机相册 10 月 4 日视频、截屏录屏相册 7 月 6 日 3 个录屏、以及「视频」相册 4 个视频均显示播放角标，可正常播放。

## 19. 同期其它修复（SMB2 枚举截断、缓存版本、日期分组等）

### 19.1 SMB2 目录枚举提前结束（大相册只显示到某一天）

**现象**：SMB 相册卡片显示的张数正确，但点进去列表只到某一天为止，后面的照片全部缺失；重启、重新扫描也不一定恢复。

**根因**：旧实现用服务端回传的 `FileIndex` 续传目录枚举：

- 首次查询带 `SMB2_INDEX_SPECIFIED`；
- 后续 `setFileIndex(_fileIndex)`，`_fileIndex` 取自上一批最后一项的 `getFileIndex()`。

实测 Samba 对 `FileIndex` 恒定返回 **0**，且目录被并发写入（例如备份正在进行）时，服务端会提前回 `STATUS_NO_MORE_FILES`。客户端把「提前结束」当成「枚举完成」，于是半截列表被写入 7 天 TTL 的缓存。

**修复**：代码位置 [smb2_files_enumerator.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_files_enumerator.dart)

- 首次查询改用 `SMB2_RESTART_SCANS`，强制从头开始；
- 后续查询**不带任何 flag**：SMB2 的枚举游标挂在目录句柄上，天然从上次位置继续，不依赖 `FileIndex`；
- 删除 `_fileIndex` 与 `SMB2_INDEX_SPECIFIED`；
- `_first()` / `_more()` 校验 `status`：只有 `STATUS_OK` 与 `STATUS_NO_MORE_FILES` 合法，其余一律抛 `SmbException`，交给上层整轮重试，**绝不把半截结果当完整列表缓存**。

### 19.2 缓存版本 v5 → v6

代码位置：[cache_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/cache_service.dart)

枚举截断期间可能已经把半截媒体列表落盘，且 TTL 长达 7 天；仅修代码不会让坏缓存失效。将 `_albumMediaCacheVersion` 从 `v5` 升到 `v6`，升级后首次进入相册强制重新完整枚举。EXIF 时间缓存不带版本，不会被重复探测。

### 19.3 刷新相册后按张数变化失效媒体缓存

代码位置：[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart)

刷新扫描前记录旧相册列表，扫描完成后对**张数发生变化**的相册调用 `invalidateAlbumMediaItems()`。否则卡片已显示新张数，点进相册仍命中旧媒体列表缓存，出现「张数对不上内容」的观感。

### 19.4 日期分组头补充年份

代码位置：[photos_screen.dart](file:///e:/Code/Projects/MiPix/app/lib/screens/photos_screen.dart)

原实现只显示 `M月d日`，导致 2025 年 8 月的照片与今年 8 月无法区分。改为：今年仍显示 `M月d日`，**非今年显示 `yyyy年M月d日`**。分组头与查看器标题共用这一规则；日期格式仅含数字占位符，不依赖 `zh_CN` 语言包初始化。

### 19.5 查看器返回后按删除结果刷新

同一文件：`PhotoViewerScreen` 以 `bool` 返回是否发生删除。`photos_screen` 只在返回值为 `true` 时重新加载列表，避免每次退出查看器都触发一次全量读取（500 张 + EXIF），减少无意义 IO 与列表跳动。

### 19.6 SMB 读流在取消订阅时关闭句柄

代码位置：[smb_file_stream.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/smb_file_stream.dart)

`smbOpenRead` 原先把 `smbCloseFile` 放在循环之后：消费者提前取消订阅（视频播放器断开、拖动进度条换区间）时，`async*` 生成器在 `yield` 处终止，`smbCloseFile` 不会执行，文件句柄持续泄漏；共享连接上的句柄累积到上限后，服务端会拒绝后续 `CREATE`。

修复：读循环包进 `try { ... } finally { await smbCloseFile(...) }`，关闭失败（连接已断）静默忽略——句柄随连接一起回收即可，不影响调用方。

## 20. 本地媒体分页与「全部备份」全量枚举（2026-10-23）

### 20.1 现象与根因

用户提出：如果手机里照片很多，固定数量限制会导致更早的照片永远读不到。

排查后的实际上限并不统一：

| 位置 | 原上限 | 原因 |
|---|---|---|
| 「照片」页 | 最近 500 张 | `getRecentPhotos(count: 500)` 写死 |
| 本地相册内页 | 前 200 张 | `getMediaItems` 默认 `pageSize: 200`，且页面的 `_loadMore()` 只在远端相册触发 |
| 「截屏录屏」虚拟相册 | 2000 条 | 在全库最新 2000 条里按路径过滤，旧截图会被漏掉 |
| 「所有照片」/「视频」虚拟相册 | 首页 200 条 | 用 `count: (page + 1) * pageSize` 的**前缀**语义取数，分页追加会重复返回前面的数据 |

上限最初是为了控制首屏成本：[_toMediaItem](file:///e:/Code/Projects/MiPix/app/lib/services/photo_service.dart) 对每张照片都要读 `File.length()`（一次 stat）并通过平台通道取 `title`、`mimeType`、`size`、`modifiedDateTime`，500 张就是上千次跨端调用，且逐张 `await` 串行执行。图库上万时一次性转换会让首屏明显变慢，但把窗口固定死、又没有分页兜底，就变成了功能缺陷。

### 20.2 浏览：绝对区间分页

- [photo_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/photo_service.dart) 新增 `totalMediaCount()`、`getMediaRange(start, count)`、`mediaCountOf(albumId)`，并把虚拟相册统一改成 **`[start, start + count)` 绝对区间**语义：
  - 「所有照片」直接对全库相册调用 `getAssetListRange`；
  - 「视频」优先读「全部视频」虚拟相册，读不到时合并各视频目录再切片；
  - 「截屏录屏」改为直接查询 `Screenshots` / `ScreenRecorder` 两个桶并分页合并，不再从全局最新 2000 条里筛。
- 「照片」页：首屏 `recentPhotoPageSize = 500`，滚动到距底部 600 px 时调用 `loadMore()`，之后每页 `mediaPageSize = 200`。刷新时若已加载超过 500 条，保持当前窗口大小，避免把滚动位置抽走。
- 本地相册内页：`albumItemsProvider` 从 `FutureProvider` 改为 `StateNotifierProvider.family`，暴露 `load()` / `loadMore()` / `hasMore`；网格滚动到底追加下一页，首屏不足一屏时用 `addPostFrameCallback` 自动补页（否则没有滚动事件可触发）。
- 追加是对旧数据的**尾部追加**，因此：
  - 不触发列表偏移补偿（只在新照片插入顶部时补偿）；
  - 不播放逐瓦片入场动画（只有真正新增的 id 才动画）；
  - 按 `MediaItem.id` 去重，防止期间新增照片导致区间偏移时出现重复瓦片。

### 20.3 「全部备份」：点击时全量枚举

浏览可以分页，但整批备份不能只看已加载窗口，否则旧照片永远不会被上传。

`PhotoService.getAllMediaPaths()` 在用户点击「全部备份」时遍历整个媒体库（`RequestType.common`，图片 + 视频）：

- 按每批 200 条调用 `getAssetListRange`，边读边解析路径，不构建整库 `MediaItem`，避免上万个 `File.length()` 与对象常驻；
- 优先用 `_directPath(asset)`（只依赖已返回的 `relativePath` / `title`），失败才回退 `_resolvePath`；
- 路径去重后与当前服务器的已备份集合比较，只把真正未同步的路径交给传输层。

传输页同时调整了文案与按钮状态：还有未加载内容时副标题显示「已加载 N 项待同步」，按钮保持可用；「本地照片都已同步」只在整库确实枚举完（`hasMore == false`）时出现。

### 20.4 验证

- `flutter analyze` 无新增问题；release 构建通过。
- 本机媒体库共 404 张、小于「照片」页首屏 500 张，也小于各相册的 200 条页大小，因此真机上不会触发第二页。分页逻辑目前通过静态检查与构建验证，等图库规模超过首屏后再做真机滚动实测（本机无法人为构造该规模，未伪造验证结论）。
