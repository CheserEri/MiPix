## 1. 单文件 SMB 备份慢（性能瓶颈）

### 1.1 现象

从手机向 SMB 服务器备份大文件（尤其视频）极慢：单文件 1.47 GB 实测 **4.78–5.00 MB/s**（四路分片并行，单路约 1.28 MB/s），持续传输时 UI 卡顿。

用户诉求：从软件本身解决，**不接受"只调并发数"**；必须先定位瓶颈再改代码。

### 1.2 根因

通过 Profile/AOT 真机计时拆解（`[diag0]` / `[timing2]`）确认，瓶颈**不在分块大小、连接数或数据拷贝**，而在 **SMB2 报文签名**：

- 真机实际协商方言为 **SMB 2.1（`0x210`）**，签名算法为 **HMAC-SHA256**（此前误判为 AES-128-CMAC，已更正）。
- 每块 64 KiB 单连接墙钟 ≈ **48 ms**：本地读 ~13.6 ms（含主 isolate 排队假象）、encode ~10 ms（**其中 ~9.8 ms 是签名**）、等待响应 ~24 ms。
- `pointycastle` 的 SHA-256 把 8 字状态与消息缓冲存成装箱 `List<int>`，每个 32 位运算都经 `clip32`/`rotr32` 包装，输入按 4 字节逐字解包 → 64 KiB 报文签名约 **9.1–9.8 ms**，微基准仅 **6.78 MB/s**（同类实现合理应有 30–50 MB/s，属**实现低效**而非算法固有开销）。
- 4 连接并发 ≈ 79 块/s × 9.8 ms ≈ **0.77 s CPU/秒**，全部在主 isolate 串行 → 占用约 90% 算力，事件循环抖动（50 ms Timer 被拖到 130–240 ms）。

真机证据：

```
[diag0] negotiated dialect=0x210 (SMB210) sigRequired=false sigEnabled=true enforced=false
[diag0] sign benchmark alg=SHA-256/HMAC bytes=65008 rounds=10 avgUs=9147 throughput=6.78MB/s
[diag0] signing=ENABLED alg=SHA-256/HMAC setupRequired=false responseSigned=true
```

补充结论：
- `sigRequired=false`：**Samba 并未强制签名**（`server signing = default`）；客户端仅因 Session Setup 响应带 `SMB2_FLAGS_SIGNED`，就在 [smb2_session.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_session.dart) 的 `isSignatureSetupRequired() || signed` 分支为整条会话开启签名。
- 库作者本意默认不签名：`Configuration.isSigningEnabled = false`、`SmbTransport._signingEnforced = false`（硬编码）。
- 服务端单次写入硬上限 **64 KiB**（`SmbStreamConsumer.blockSize = 64936`），加大分块会触发 `STATUS_INVALID_PARAMETER`，此路不通。
- `SmbTransport.sendrecv` 全程持有 `sendrecvMutex`，一条连接同一时刻仅 1 个请求在途。

### 1.3 方案（决策：路线 C）

**路线 C：保留 SMB 签名，优化 HMAC-SHA256 实现。** 先做纯 Dart 热路径优化，把 65,008 B 签名稳定压到 ≤2.2 ms（≥30 MB/s）；未达标再评估 C-FFI（Android 原生 HMAC）。

- 仅改一个文件：[smb2_signing_digest.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_signing_digest.dart)
  1. 新增 `_MacLike` 抽象接口：`_PointyMac` 包装 pointycastle `Mac`，`_CryptoHmac` 包装 `package:crypto`。
  2. **SMB 2.0.2 / 2.1 分支改用 `package:crypto` 的 `Hmac(sha256, sessionKey)`**——其 SHA-256 全程使用 `Uint32List`，同长度输入快约一个数量级。
  3. **SMB 3.0/3.0.2/3.1.1 仍保留 pointycastle 的 `AES/CMAC`**，协议行为不变。
  4. `_CryptoHmac.doFinal` 用 `Uint8List.view(...)` 零拷贝视图交给 crypto，避免额外复制。
  5. 签名语义与规范一致：清签名域 → 置 `SMB2_FLAGS_SIGNED` → 计算 MAC → 前 16 字节写入签名域。
- `crypto: ^3.0.3` 已是 smb_connect 现有依赖，无需新增。
- 回滚实测零收益的 `extensions.dart` 三处 `setRange` 拷贝改写，删除全部临时诊断插桩（`SmbTiming`/`EncodeDiag`/`[timing*]`/`diagReconcileLog` 等）。

**未被采纳的路线**：A（关闭签名，非严格合规、降低完整性保护，仅作对照/可选模式，不作默认）、B（SMB 写路径拆分到多 isolate，改动量大，暂不做）。

### 1.4 结果（验收门槛全部达成）

签名微基准（65,008 B × 10 轮，Profile/AOT 真机）：

| 实现 | 耗时 | 吞吐 |
|---|---:|---:|
| `package:crypto` HMAC-SHA256 | 1,475 µs | **42.03 MB/s** |
| `pointycastle` HMAC-SHA256 | 9,680 µs | 6.40 MB/s |

- 加速约 **6.6 倍**；交叉验证 `sign cross-check crypto==pointycastle: true`（签名字节完全一致）。

大文件端到端（1,466,810,721 B，四路分片）：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| 吞吐 | 5.00 MB/s | **19.477 MB/s** | **+289%（约 3.9 倍）** |
| 事件循环最大间隔 | ~136 ms | **72 ms** | 抖动收敛 |

- 正确性：远端 SHA-256 `324ee621c5e9aadbe1bbce89fc0fe46cfdaa3e9b360189f5742867cc816e8468` 与本地一致；远端大小一致。
- 无回归：reconcile 386 张照片全部匹配；签名仍开启、SMB2.1 验签通过。

| 验收门槛 | 目标 | 实测 | 结果 |
|---|---|---|---|
| HMAC 微基准 | ≥30 MB/s | 42.03 MB/s | ✅ |
| 大视频吞吐提升 | ≥30% | +289% | ✅ |
| 远端 SHA-256 一致 | 必须 | 一致 | ✅ |
| UI 事件循环抖动收敛 | 明显收敛 | 136→72 ms | ✅ |
| 小文件/失败重试无回归 | 无回归 | 386/386 | ✅ |

**结论：纯 Dart 阶段目标达成，无需进入 C-FFI / A / B 备选路线。**

### 1.5 遗留项（可选）

静态审查对本次改动提出三条完善建议（非当前故障）：
1. 明确 `_CryptoHmac.update` 的输入约束：当前只保存最近一次 `update` 的数据，多次调用会覆盖；现调用路径仅单次调用，故成立。建议支持增量输入，或用注释/断言限制「每次摘要只允许一次 update」。
2. `_CryptoHmac.doFinal` 结束后仍保留 `_data` 对最近报文的引用，直到下一次 `reset`；建议在 `try/finally` 中清空 `_data`/`_offset`/`_length`。
3. 补充签名单元测试：覆盖重复调用、非零偏移及切片输入、与 pointycastle 签名字节一致、篡改后验签失败、SMB3 AES-CMAC 不回归。

> 优先级（用户已拍板）：**单元测试最高，输入约束次之，内存清理最低**；三项均不影响已达成的性能指标。

## 2. listFilesWithSize 间歇性失败导致对账误判「已备份 0」

### 2.1 现象

日志中同一批相册反复出现：

```
[diag-smb] listFilesWithSize FAIL path="相机" err=The system cannot find the file specified.
（连续 7 个相册全部 FAIL）
[reconcile] 1791830725307 候选 387 → 已备份 0
```

远端清单间歇性全部失败，随后「与服务器核对」把所有已备份记录整体清空（**不可逆的数据损失**）。

### 2.2 根因

调用链：`SmbService.listFilesWithSize` → `_getConnection`（共享缓存连接，key = `host:username`，TTL 1 分钟）→ `connect.file(smbPath)` → `connect.listFiles(folder)`。

- 异常抛出点：[smb2_files_enumerator.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_files_enumerator.dart#L38-L59) 对目录发 `CREATE(FILE_DIRECTORY_FILE)`，status ≠ OK 时抛 `SmbException`。`The system cannot find the file specified.` 对应 `NT_STATUS_NO_SUCH_DEVICE/NO_SUCH_FILE/OBJECT_NAME_NOT_FOUND`。
- 注意：`connect.file()` 对 not-found **不抛异常**，只返回 `SmbFile.notExists`，所以错误只在 `listFiles` 处暴露。

日志证据（已核对历史 logcat）：

| 观察 | 结论 |
|---|---|
| 同一进程 03:16:46 全 7 FAIL；03:27:53 全 7 SUCCESS（相机106/原神109/漫画44/DJI6） | 排除「路径/配置不符」 |
| FAIL 间隔仅 8–13 ms（≤1 个往返）；SUCCESS 每个约 300 ms | 失败调用**没有**做真正的目录枚举，被服务端立即拒绝 |
| 03:36:13 同批全 FAIL，但该批用**全新连接**（`createConnection`）成功上传 387 项 | **问题在共享缓存连接**（全新连接不受影响） |
| 04:44:41 冷启动全 SUCCESS，`候选 387 → 已备份 387` | 失败是**间歇性**的，非确定性 |

放大路径（已由源码确认）：
- **已确认的软件缺陷**：`listFilesWithSize` 把所有异常吞掉返回空表；`reconcileWithServer` 把空表当作远端权威结果 → `replaceSynced(serverId, stillSynced)` **整体覆盖** → 记录被清成 0。与代码注释「网络异常时放弃、不改记录」的既定意图不一致。
- **最可能触发因素**：复用共享缓存连接，共享连接出现瞬时失败（假设，未最终定论；**不得写成已证实根因**）。
- `reconcileWithServer` 仅用 `testConnection`（IPC$ `listShares` 探活）前置校验，对 MyDoc 各相册 not-found 时**探活不足以拦截**。

### 2.3 方案（decision-complete）

**变更 1 — `listFilesWithSize` 区分「读取失败」与「远端为空」**（[smb_service.dart](file:///e:/Code/Projects/MiPix/app/lib/services/smb_service.dart#L167-L203)）
- 返回类型 `Future<Map<String, int>>` → `Future<Map<String, int>?>`：`null` = 读取失败（不可信）；`{}` = 目录不存在或为空（远端确实没有）。
- try 前先算 `smbPath`；`connect.file(smbPath)` 后 `folder.isExists == false` → 打印 `ABSENT` 并 `return {}`；目录存在才 `listFiles`，最多 3 次总尝试（首次 + 2 次重试），每次重试前 `_invalidateConnection` 并重新获取连接；重试耗尽打印含 `path/smbPath/share/rootPath/host/err` 的 FAIL 日志并 `return null`。
- 复用 `isConnectionError` 判断可重试性；not-found 族在「目录已存在」前提下同样视为异常参与重试。

**变更 2 — 对账「清单不完整即整轮放弃，不覆盖记录」**（[transfer_provider.dart](file:///e:/Code/Projects/MiPix/app/lib/providers/transfer_provider.dart#L143-L173)）
- 抽出顶层纯函数（便于单测，与 `UploadFailureGuard`/`uploadWithRetry` 同风格）：

```dart
/// 计算「核对后仍视为已备份」的路径集合。
/// 任一相册清单为 null（读取失败）→ 返回 null，表示本轮清单不完整、应放弃。
Set<String>? reconcileSynced({
  required Iterable<String> candidates,
  required Map<String, String> albumOf,                  // 本地路径 → 相册名
  required Map<String, Map<String, int>?> remoteIndex,   // 相册名 → 清单（null = 失败）
  required Map<String, int> localSizes,                  // 本地路径 → 大小；缺失 = 已删除/不可读
});
```

- `reconcileWithServer` 结果为 `null` → 打印「清单不完整（存在读取失败的相册），放弃本轮，保留现有记录」并 `return`，**不调用 `replaceSynced`**。
- 语义细节：本地已删除 → 丢弃记录；相册名为空 → 不参与对账；`size > 0 && remoteSize == size` → 保留。

**变更 3 — 备份路径遇到未知远端清单时的处理**
- 初版：`null` 时「跳过去重、照常上传」（避免一次抖动导致整相册静默跳过）。
- **后续收紧（同名冲突方案）**：改为 **fail-closed** —— 清单不可读时该组候选全部记 `failUnknown`（可重试失败），不写入任何远端文件。二者取舍见第 3 节。

**变更 4 — 单元测试**（[transfer_recovery_test.dart](file:///e:/Code/Projects/MiPix/app/test/transfer_recovery_test.dart)）
- `reconcileSynced`：某相册清单为 `null` → 返回 `null`；key 缺失 → 放弃；空 map → 全部判未备份；命中「同名同大小」保留、同名不同大小不保留；本地已删除 → 丢弃；空串相册不参与且不影响完整性判定。共 6 个用例（`group('reconcileSynced')`），总 17 项全通过。

### 2.4 结果与验证

- 单测：`flutter test test/transfer_recovery_test.dart` → **All tests passed!（17 项）**。
- `flutter analyze` 改动文件无新增告警（既有 7 条位于 smb_service L17/51/240/611/612，未动）。
- 真机（release，同签名 `install -r` 未清数据）：冷启动 05:01:38 七个相册全部 `listFilesWithSize` 成功，无 FAIL/ABSENT；`[reconcile] 候选 391 → 已备份 387`，**未出现「→ 已备份 0」**（故障基线为 `候选 387 → 已备份 0`）；无 `StreamSink is closed` 等未处理异常。
- 本轮未复现 FAIL，「清单不完整」日志由单测覆盖替代。

### 2.5 残留风险

- 库层「共享连接树瞬时失效」机制未最终定论；若 `null` 仍频繁出现，需在 [smb_connect.dart](file:///e:/Code/Projects/MiPix/app/packages/smb_connect/lib/src/connect/smb_connect.dart#L130-L138) 排查 `shareTree` 复用。
- 历史被清空的记录不可恢复，本修复只保证不再发生。
- 长时息屏对照（≥5 分钟）本轮未补测，不计入验收。

## 3. 增量备份「同名文件冲突」处理

### 3.1 现象

仅用「文件名 + 大小」判断远端是否已有待备份文件，会出问题：
1. 同名同大小可能内容不同 → 直接跳过会漏备份更新内容。
2. 同名不同大小可能发生覆盖 → 较大版本也可能被较小版本替换。
3. 不同相册中的同名文件对应不同远端路径，不应视为冲突。
4. 同一批次多个本地文件可能指向同一远端路径；只保留先处理的会**依赖遍历顺序**。
5. 远端清单读取失败若被当成「目录为空」，会在未知远端大小下继续覆盖。

### 3.2 判定规则（以**远端目标路径** = 相册目录 + 文件名为准）

| 情况 | 处理 | 提示 |
|---|---|---|
| 远端无该目标路径 | 正常上传 | 无 |
| 同名、大小不同、本地较大 | 上传并替换远端 | 「已用较大版本更新远端文件」（可选） |
| 同名、大小不同、远端较大 | 保留远端，拒绝上传 | 「远端已有更大的同名文件，本次未覆盖」 |
| 同名、大小相同 | 双方 SHA-256 后决定 | 见下 |
| 两相册各自同名 | 各按各自路径处理，都可上传 | 不提示冲突 |
| 同批次多个本地文件 → 同一远端路径 | 先比较大小，按规则择一，不依赖遍历顺序 | 未选中者给原因 |
| 远端清单/文件信息不可读 | **不假设远端不存在**；fail-closed 跳过受影响文件 | 「无法读取远端信息，未备份，请检查连接或权限后重试」 |

同名同大小哈希规则：仅对「路径相同 + 大小相同」的候选做 SHA-256（流式读取，不入内存）。相同 → 视为内容相同、跳过并标记已同步；不同 → **默认保留远端**、跳过本地并提示「同名同大小但内容不同，远端文件已保留」。

### 3.3 方案（实施要点）

## 4. 息屏后备份中断与保活锁

### 4.1 现象

大批量备份时息屏一段时间后再点亮：传输速度归零、进度条静止、任务既未明确完成也未明确失败（看似「卡死」）。

### 4.2 取证与根因

现场时间线（Redmi K20 Pro，`com.chesereri.mipix` 1.0.7+8，NAS `192.168.31.184`）：

| 时间 | 事件 |
|---|---|
| 02:21:02 | 应用进程 28166 启动 |
| 02:29:06 | 息屏（`Going to sleep due to timeout`） |
| 02:29:13 | 进入 DOZE |
| 02:30:48 | **首条异常** `Unhandled Exception: Bad state: StreamSink is closed`（息屏后约 100 秒） |
| 02:30:48~02:32:03 | 同类异常密集出现，共 83 条 |
| 02:34:01 | 仍在重复抛出（取证时点） |

调用栈（节选）：

```
#2 SocketWriter.write (package:smb_connect/src/utils/socket/socket_writer.dart:16)
#3 SmbTransport.doSend (package:smb_connect/src/connect/smb_transport.dart:739)
#4 SmbTransport.sendrecv (...:666)
#8 SmbService._deleteRemoteIfExists (package:mipix_app/services/smb_service.dart)
#10 SmbService.uploadFileVia (...)
#11 TransfersNotifier.backupPhotos.runItem (package:mipix_app/lib/providers/transfer_provider.dart)
```

异常统计：`Bad state: StreamSink is closed` 83 次；`TimeoutException` 0；`SocketException` 0；`Connection reset` 4。**没有任何"网络不可达"类系统级错误**，全部表现为「socket 已关闭但仍在写入」。

**排除的猜想**（息屏+卡死时取证）：
- ❌ 不是 Doze 掐断网络：ping NAS 成功（0% loss，avg 19.3 ms）、WiFi 已连接 866 Mbps、445 端口可连。
- ❌ 不是应用被冻结/杀死：进程存活（CPU 仍在消耗）、**未持有任何 wakelock**、从未申请 WifiLock、不在电池优化白名单、全仓库无前台服务/WakeLock/WifiLock 实现。

**根因（两层叠加）**：
1. **触发层**：传输期间完全未申请 `WifiLock`/`PARTIAL_WAKE_LOCK`；息屏后无线省电导致 SMB over TCP 会话被断开（`SocketWriter.write → _Socket.add → StreamSink is closed`）。
2. **放大层**：断连后无法恢复并持续空转——
   - `isConnectionError()` **不识别** `Bad state: StreamSink is closed` 这类 socket 关闭错误 → 重试/重连逻辑不生效，文件被判失败，且异常**逃逸为未捕获异常**，批量任务无法收敛。
   - 缓存连接 `_getConnection` 挂了 `onDisconnect`，但**传输实际使用的 `createConnection` 没有挂**，连接死掉无人感知。
   - 没有「等待网络/屏幕恢复再续传」机制：每文件经历 15–30 秒超时空转（库内 3 秒 × 5 次重试 + `_stallTimeout = 30s`），大文件量下进度条冻结数小时。

> 复核结论（2026-10-14）：现有材料足以说明「某条 socket 已关闭而应用仍向其发送请求」及「连接类错误识别与批次恢复能力不足」，但**不能证明 Wi-Fi 息屏省电就是本次断连的直接原因**，应保留为待验证假设，不写成已确认根因。

### 4.3 方案

**方案一（必做）：传输期间保活**——批次运行期间在原生侧持有 `WifiManager.WifiLock(WIFI_MODE_FULL_HIGH_PERF)` + `PowerManager.PARTIAL_WAKE_LOCK`，批次结束释放。改动点：
- [MainActivity.kt](file:///e:/Code/Projects/MiPix/app/android/app/src/main/kotlin/com/chesereri/mipix/MainActivity.kt)：新增 MethodChannel（`mipix/keepalive`），提供 `acquire`/`release`。
- [AndroidManifest.xml](file:///e:/Code/Projects/MiPix/app/android/app/src/main/AndroidManifest.xml)：新增 `WAKE_LOCK`、`ACCESS_WIFI_STATE`、`ACCESS_NETWORK_STATE` 权限。
- [transfer_provider.dart](file:///e:/Code/Projects/MiPix/app/lib/providers/transfer_provider.dart)：批次进入 `acquire`、`finally` 中 `release`。
- 不需要前台服务/通知栏/MIUI「省电无限制」。诚实说明：「绝对不中断」无工程保证（路由器/NAS 侧也可能主动断开），但能消除「一息屏就断」主因。

**方案二（必做）：断线后在开屏/网络恢复时自动 SMB 重连续传**
1. 给 `createConnection` 补 `onDisconnect` 回调（与缓存连接一致），连接一死立即标失效。
2. `isConnectionError` 纳入 socket 关闭类错误（`streamsink is closed`、`socket is closed` 等**明确本地 socket 关闭错误**，不要以过宽的 `bad state` 匹配所有程序错误），并阻止此类异常逃逸为 `Unhandled Exception`。
3. 通过 MethodChannel 注册 `ConnectivityManager.NetworkCallback` + `ACTION_USER_PRESENT`/亮屏广播，回传 Dart；批次置 `paused`（暂停而非失败，**保留剩余队列**），事件到达后重建连接池续传。
4. 兜底：长时间无法恢复则整批判失败，保留 `retryFailedUploads` 手动续传入口。

**方案三（加固）：失败快速收敛**——连续 N 次连接类失败即中止整批（或转 paused），避免每文件各自空转 15–30 秒；与方案二共用同一状态机。

> 幂等性：大文件分片上传采用「按字节区间覆盖写 `.mipixtmp` → 全部写完 rename」，断线后重传同一文件是幂等的，不会留下半截"锁死"文件。但该结论需覆盖不同失败时机（旧分片仍在运行、超时但服务端仍处理、清理临时文件失败、重连与重试交叠）验证。

### 4.4 保活锁引用计数修复（已实施）

**问题（静态审查第 5 项 + 历史教训）**：全局布尔值标记持有状态，会导致重叠备份批次互相顶掉锁 → 息屏后无锁上传。且并发申请时（第一次原生申请未完成），第二个调用递增计数后立即返回；若第一次申请失败，异常处理只减一次计数，计数仍可能 > 0 但原生锁实际未持有。

**方案**：保活锁改为**引用计数**——仅在计数 **0→1** 时申请原生锁、**1→0** 时释放；串行化原生申请与释放，或记录原生锁是否确实获取成功，确保仍在运行的批次可重新申请。

**结果**：14 项应用侧测试全部通过；真机验证显示多批次备份场景下保活锁可连续持有至对应批次结束，息屏期间锁正常生效，无 `StreamSink is closed` 或未处理异常，所有任务完成无失败。（当前设备无待备份照片，5–10 分钟息屏长批次验证需用户拍摄新照片或授权 adb 推送测试文件触发。）

### 4.5 风险与待确认

- 本机当时安装的 APK 堆栈行号与当前工作区源码**对不上**（装的不是当前源码），修复后必须重新构建安装才能验证。
- 需新增 3 个权限，需用户确认；重装若签名不同会**清空应用数据**（历史教训），需提前备份配置。
- Android 14 起 `WIFI_MODE_FULL_HIGH_PERF` 已弃用并被映射为 low-latency 模式，可能增加耗电、硬件不支持时可能无效，须在目标机型实测。
- 若产品目标是「启动备份后切后台/息屏仍持续传输」，需评估前台服务及常驻通知（当前 `targetSdk = 35`，需遵循对应前台服务类型与限制）；若允许息屏暂停，则实现明确暂停/恢复 + 安全续传。**无论哪种模式，都要保证旧 worker 退出后才恢复队列。**

## 8. 关键工程约束速查

- **64 KiB 硬上限**：Samba 4.19 单次写入上限 64 KiB，客户端 `_uploadChunkSize = 64936`，加大触发 `STATUS_INVALID_PARAMETER`。
- **临时文件 + 原子改名**：上传一律写 `.mipixtmp`，全部写完再 rename；失败不暴露半成品；断线重传幂等。
- **签名**：SMB2.1 用 `package:crypto` HMAC-SHA256（已优化），SMB3 用 pointycastle AES-CMAC；签名语义（清签名域 → 置 `SMB2_FLAGS_SIGNED` → 计算 MAC → 前 16 字节写入）不变。
- **`maxWriteSize`**：smb_connect 协商返回的是客户端侧计算值，不代表服务端真实能力，不可直接作为分块依据。
- **缩略图三级缓存**：内存 → 磁盘 → 远端 EXIF 内嵌缩略图；7 天 TTL + 上限淘汰。
- **保活锁引用计数**：仅 0→1 申请、1→0 释放，避免重叠批次互相顶掉锁。
- **增量备份 fail-closed**：清单读取失败不写入该目录任何文件，并给可重试原因与 UI 文案。
- **状态管理**：flutter_riverpod，按 app/photo/album/smb/transfer 模块划分 provider；相册分组遵循「系统/我的/更多」三段结构。
- **媒体库**：photo_manager 对接 Android MediaStore；图片查看器用自研 `_ZoomableImage` 避免与 PageView 手势冲突。
- **FUSE 云隐（GPS）**：Android 10+ 缺 `ACCESS_MEDIA_LOCATION` 时，读照片会把 EXIF 位置信息数值区间置 0 且**文件长度不变**；必须在读取前持有该权限。裸路径读取无法用 `setRequireOriginal()`。
- **上传后回读校验**：rename 之前必须把远端临时文件读回算 SHA-256，与本地一致才改名；不一致则删临时文件并报错（成本约翻倍：每个上传项多一次本地哈希 + 一次完整远端回读）。
- **拍摄时间回写**：上传成功后用拍摄时间 `setFileTime` 回写远端文件时间，否则备份端时间会变成备份时刻。
- **`lastModified` 单位**：SMB 返回的时间戳已是毫秒，转 `DateTime` 时不要再乘 1000。

## 9. 备份端照片时间戳与手机相册不符

> 时间：2026-10-15　状态：已修复并真机验证

### 9.1 现象

备份到 NAS 的相机相册照片，时间戳与手机相册里的拍摄时间不一致：部分显示成备份时刻，部分在文件管理器里显示成离谱年份。

### 9.2 根因（两处）

1. **上传不携带拍摄时间**：`smb_connect` 没有 `setFileTime` 能力，文件写完后远端时间由 Samba 设为「服务端写入时刻」，于是备份端时间 = 备份时间。
2. **读取侧多乘了 1000**：SMB 相册浏览用 `DateTime.fromMillisecondsSinceEpoch(file.lastModified * 1000)`，而该值本就是毫秒，结果被放大 1000 倍，日期显示成公元数万年。

### 9.3 方案

- **抽象层**：`SmbConnect.setFileTime(file, {lastWriteTime, createTime, lastAccessTime, changeTime})`，默认实现抛 `UnsupportedError`。
- **SMB2 实现**：`SMB2 SET_INFO` + `FILE_BASIC_INFO`，以 `FILE_OPEN` + `FILE_WRITE_ATTRIBUTES` 打开；`attributes` 传 0（`FILE_BASIC_INFORMATION` 语义为不修改文件属性）；`createTime` 默认沿用 `lastWriteTime`，`lastAccessTime`/`changeTime` 传 0 表示不修改；非 `NT_STATUS_OK` 抛 `SmbException`。
- **主流程**：上传成功且改名完成后调用 `_applySourceTime` 回写；回写失败只记日志，不影响备份结果。
- **拍摄时间来源**：`PhotoService.captureTimesForPaths`（按 `relativePath` 规范化建索引，命中 EXIF 拍摄时间，未命中回退 `File.lastModified()`）；`transfer_provider` 创建任务时带上 `captureTime`，上传时作为 `sourceTime` 传入。
- **读取侧**：删掉多余的 `* 1000`。

### 9.4 代码位置

| 位置 | 说明 |
|---|---|
| `app/packages/smb_connect/lib/src/connect/smb_connect.dart` | 抽象 `setFileTime` |
| `app/packages/smb_connect/lib/src/connect/impl/smb2/smb2_connect.dart` | SMB2 `setFileTime` 实现 |
| `app/packages/smb_connect/test/file_basic_info_test.dart` | 新增：`FILE_BASIC_INFO` 编解码单测 |
| `app/lib/services/smb_service.dart` | `_applySourceTime`（两条上传路径各调用一次）；修正 `* 1000` |
| `app/lib/providers/transfer_provider.dart` | `_PendingUpload.captureTime` → `sourceTime` |
| `app/lib/services/photo_service.dart` | `captureTimesForPaths` |

### 9.5 结果与验证（真机）

覆盖安装到 Redmi K20 Pro（Android 11）后重新备份，备份端照片时间与手机相册拍摄时间**完全一致**，应用配置无丢失。新增 `file_basic_info_test.dart` 单测防止该逻辑退化。

## 10. 备份端照片 GPS 位置信息丢失（Android FUSE 云隐）

> 时间：2026-10-15　状态：读侧已修复并真机验证；历史副本策略待决策

### 10.1 现象

备份到 NAS 的照片，EXIF 里的 GPS 为空（经纬度全 0）；而手机相册里同一张照片的 GPS 正常。时间与画面内容都正确，唯独位置信息丢失。

### 10.2 根因

Android 10 起，应用若缺少 `ACCESS_MEDIA_LOCATION`，`MediaProvider` 的 **FUSE 层**会在应用读取照片时**把 EXIF 中位置信息的数值区间替换为 0**，而**文件长度与其余字节完全不变**。

三个致命后果：

1. `File(...)` 裸路径读取拿到的就是被云隐后的字节；
2. 「同名同大小」去重与 SHA-256 校验都察觉不到（长度没变）；
3. 应用「忠实地」把这些被云隐的字节写进 NAS，GPS 就永久丢了。

> 注：`MediaStore.setRequireOriginal()` 只作用于 **URI 路线**。本工程读取全程是裸路径（自行拼 `/storage/emulated/0/DCIM/Camera/...` 再 `File(...).open()`），没有 URI，故该 API 不适用；`photo_manager` 的 `originFile` 在 Android 11 上返回的也是同一路径。

### 10.3 取证（只读实测，2026-10-15）

样本 `/storage/emulated/0/DCIM/Camera/IMG_20260725_180930.jpg`（3,239,398 B，含 GPS）：

| 读取方 / 状态 | SHA-256 | EXIF GPS |
|---|---|---|
| 原件（PC 上小米云下载副本） | `631dbdc1582c6cc5b04b943d70fb74e9bd3bc7e8d0c24408fb6c194aca127780` | 40.286106, 122.15085 |
| 设备 shell（`sha256sum`） | 同上 | — |
| 应用 · **未授予**权限 | `c2cbe33af70b2cfab97f7758694d4534c1b52f7a57aeffa73c0ed16295fffec6` | 0.0, 0.0 |
| 应用 · **已授予**权限 | `631dbdc1…7780`（= 原件） | 40.286106, 122.15085 |

结论：**Android 11 上，持有 `ACCESS_MEDIA_LOCATION` 后裸路径读取即返回未云隐的原件字节**。取证用临时只读探针完成，全程未写 NAS；探针已删除。

### 10.4 方案（全部已实施）

1. **读侧前置授权**：读取前申请 `ACCESS_MEDIA_LOCATION`（`MainActivity.ensureMediaLocation`，通道 `mipix/permission`），`AndroidManifest` 声明该权限。
2. **上传后回读校验**：`smb_service` 新增 `_hashLocalFile` / `_hashRemoteVia` / `_verifyUploadedTemp` —— 把远端临时文件读回来算 SHA-256，与本地一致才允许 rename；不一致则删除临时文件并抛错，正式文件名上始终保留旧文件。两条上传路径（单连接 / 并行分块）都在 rename 之前调用。
3. **不完整备份可见化**：`PhotoService.mediaLocationGranted`（`ValueNotifier`）→ `mediaLocationGrantedProvider` → 传输页顶部提示条 + 「去授权」按钮；授权被拒时明确告知「本次备份不含位置信息」，而不是只打日志。

### 10.5 验证（真机，2026-10-15）

用修复后的读取路径按正式备份流程上传同一张样本，NAS 端独立核对：

## 11. 界面静止仍满帧出帧的空转（缩略图误把无限循环 GIF 当动图解码）

### 11.1 现象

- 冷启动后停在照片时间轴（界面静止、无可见动画、无传输任务），进程 CPU 长期 ≈**86%
  单核**，60Hz 面板下持续 ≈**47fps** 出帧。
- 备份期间叠加这份开销后，表现为长时间无日志、主 isolate 满载——与用户感知的「传输卡住」一致。

### 11.2 根因

`Image.file` 对 `codec.frameCount > 1` 的图片返回 `MultiFrameImageStreamCompleter`
（`painting/image_provider.dart` → `FileImage.loadImage`），其 `_handleAppFrame`
（`painting/image_stream.dart`）会在下一帧时刻通过
`scheduleFrameCallback` → `scheduleFrame` **自续调度**；`repetitionCount == -1`
（无限循环动图）时永不终止。只要还存在 listener，界面静止也会满帧出帧。

缩略图（照片网格 + 相册封面）用 `Image.file(path, cacheWidth: 400)` **直接解码原图文件**，
于是相册里两个无限循环 GIF 的缩略图也走多帧解码路径。

次要放大：系统无障碍（a11y，`enabled_accessibility_services` 含 MIUI 安全中心服务）开启时，
每帧会额外遍历一遍语义树。此项非出帧驱动，仅为伴生开销。

## 13. GPS 修复后传输耗时增加与校验优化建议

> 时间：2026-10-16　状态：P0/P1 已实施（阶段文案、阶段日志、队列清理与排序），真机备份复测待执行
>
> 范围：解释 GPS 数据修复后「全部备份」体感变慢的原因，区分权限/元数据处理与上传后 SHA-256 回读成本，并记录不降低完整性保证的优化路径。

### 13.1 结论摘要

性能明显下降的主要原因不是 GPS 字节或 GPS 权限本身，而是 GPS 修复同期加入了「上传后完整回读远端临时文件并计算 SHA-256」：文件上传完成后，必须先从 NAS 再读回完整内容，与本地 SHA-256 比较，匹配后才能把 `.mipixtmp` 改名为正式文件。大文件的这段时间上行流量接近零，但 SMB 下行仍在传输，因此 UI 容易被理解为卡住。

GPS 修复仍然必要：Android 10+ 的 MediaProvider/FUSE 在缺少 `ACCESS_MEDIA_LOCATION` 时可能云隐 EXIF GPS，长度不变但内容改变。授权后上传真实原始字节，修复了数据正确性。额外回读校验则提供端到端完整性保障；二者是同一修复版本里的不同成本来源，应分别看待。

### 13.2 当前代码路径（静态核对）

1. `PhotoService.ensurePermission()` 在媒体访问授权成功/受限时调用 `ensureMediaLocationAccess()`。该权限让后续文件读取能够保留 GPS；没有证据表明权限获取本身会降低持续 SMB 吞吐。
2. `TransferNotifier._backupPhotosImpl()` 在备份开始时调用 `captureTimesForPaths()` 查找拍摄时间。该方法会分页扫描媒体库（每页最多 200 项）直到找到全部目标或扫描结束；大批量任务可能有独立的启动延迟，但不是大视频上传结束后数分钟低上行的原因。
3. 大文件由 `SmbService.uploadFileParallel()` 按多个字节区间、多条连接写入同一个临时文件。小文件由 worker 连接池调用 `uploadFileVia()`。
4. 两条上传路径都会调用 `_verifyUploadedTemp()`：先完整读取本地文件算摘要，再通过单连接 `_hashRemoteVia()` 读回远端临时文件算摘要；读取超时、大小不符或哈希不同均失败关闭，不执行 rename。
5. `PhotoService.hashFile()`（用于同名同大小冲突比较）使用 `Isolate.run()`；但上传后 `_hashLocalFile()` 当前在调用方 isolate 中执行。远端 SMB socket 读取在该连接所在 isolate 完成。
6. 上传分片连接在 `uploadFileParallel()` 校验前已经关闭；回读校验使用独立的 `setup` 连接。因此「直接复用上传分片连接」不是当前实现的行为，若要并行回读需要新建/管理并发读取连接。

### 13.3 为什么体感会下降

- **额外远端 I/O 是主因**：上传 1.4 GB 后，校验又要从 NAS 读约 1.4 GB。报告中的真机样本上传约 70 秒，回读校验约 298 秒；此时 TX 接近零、RX 持续增长，与回读校验路径一致。
- **远端读并发度低于写入**：大文件上传按多连接分片并行，上传后回读当前是单连接顺序读。读缓冲从 4095 调到 64936 已提高单连接吞吐，但无法消除单连接请求/响应吞吐上限。
- **本地文件也被再次读取**：`_hashLocalFile()` 在上传后再扫一遍源文件。它增加本地 I/O 和 CPU，但相比远端完整回读通常不是大文件总耗时的主项；其是否影响 UI 响应应以真机 profile 测量。
- **队列展示会放大等待感**：历史失败项排在新任务前面时，实际运行任务和校验进度不容易看到。该点影响可观察性，不改变传输耗时。
- **其他可测启动成本**：`captureTimesForPaths()` 的媒体库扫描、远端清单读取、同名同大小冲突比较（`hashRemoteFile()` + 本地哈希）发生在写入前，需与上传后校验分开计时，避免把不同阶段混为一谈。

### 13.4 关于「所有文件上传完后统一计算 SHA-256」

该方案要区分本地摘要和远端摘要：

- **统一延后远端回读不会减少总网络字节或校验工作量**：仍需从 NAS 读取每个文件的全部内容。它只把每文件上传后的等待移动到整批上传结束之后，整批正式完成时间不会因此必然缩短。
- **延后会推迟所有文件的 rename/成功状态**：若继续保持「校验通过后才改名」，批次中的文件在统一校验结束前都只能保留为临时文件。若上传后先 rename、之后再验，则验失败时正式路径已经暴露错误内容，失去当前原子完整性语义，不建议这样做。
- **批次中断的恢复成本变大**：更多临时文件会在最终校验前等待；应用退出、断网或存储空间不足时需要额外持久化校验队列与恢复状态。
- **可以减少上传后的本地重读**：本地 SHA-256 可在上传数据流经过时累计，或与上传并行计算；但普通 SHA-256 必须按文件字节顺序更新。多分片各自得到的摘要不能直接拼接成整文件 SHA-256。更简单的并行做法是让单独的本地 isolate 计算完整文件摘要并与上传重叠，但磁盘读取总量未减少。
- **上传流中的本地摘要不等于远端校验**：它只能记录客户端读出/发送的数据，不能证明服务端最终落盘字节相同。若要检出 NAS 写入错乱、短写或存储侧静默损坏，仍需读回远端或采用服务端可信校验机制。

结论：不建议仅把远端校验改成批次末尾统一计算。优先在不改变 fail-closed 与先验后改名语义的前提下，降低单文件校验时长，并减少/重叠本地摘要读取。

### 13.5 建议的修改顺序

#### P0：把阶段和耗时展示清楚（低风险）

- 任务阶段清楚区分「准备/冲突比对」「上传」「NAS 回读校验」「改名与时间戳回写」。
- 校验阶段显示已读/总量、当前读取速度和阶段耗时；上传阶段与校验阶段使用不同文案。不要只把两段合成一个 0–100% 进度，让大文件校验期间看起来像上传停滞。
- 增加阶段级耗时日志：媒体库拍摄时间查询、远端清单、冲突哈希、上传、本地摘要、远端摘要、rename、时间回写分别计时。每项应带远端路径/任务 ID、字节数和有效吞吐，避免记录密码等敏感配置。

#### P1：修复队列可见性（低风险）

- `backupPhotos()` 新建任务前，按 `serverId + localPath` 精确移除该文件的历史失败上传记录，避免新批次重复项被旧记录淹没；不要删除其他服务器或其他路径的失败项。
- 队列排序建议为运行中、等待中、近期终态、较早终态；或将终态历史折叠。保证当前批次运行项一打开即可见。
- 现有 `retryFailedUploads()` 已在重试前移除旧失败记录，可抽出共用的按目标身份清理逻辑，避免「重试失败」与「全部备份」行为分叉。

#### P2：重叠或消除本地二次读取（中风险）

- 先测 `_hashLocalFile()` 是否在主 isolate 造成明显事件循环抖动。若有，使用 isolate 对本地文件做流式哈希，并与上传并行；SMB 连接操作仍留在创建它的 isolate。
- 后续可评估上传与本地 SHA-256 共用同一份本地数据流。小文件 worker 上传可自然按块顺序更新摘要；大文件分片则需单独的有序哈希流，不能把各片段 SHA-256 直接拼接。若实现复杂或争用本地存储 I/O，采用并行本地哈希方案即可。
- 任一模式都需核对哈希期间文件长度/修改时间或内容版本，避免本地文件在上传与哈希之间变化而产生错误结论。

#### P3：优化远端校验吞吐（中高风险，需原型及真机验证）

- 对大文件实现多连接区间读取：每连接读取明确的 `[start, end)` 范围，读取块带 offset/序号，按文件顺序进入单个 SHA-256 chunked sink。
- 使用固定大小块和有界重排缓冲；禁止把每个大分片整体缓存后等待前序分片，否则内存随文件大小增长。
- 每段读取需验证起止偏移、累计字节数、远端初始/结束大小；任一连接失败、短读、超时或摘要不完整均 fail-closed，删除/保留临时文件按既有清理策略处理，绝不 rename。
- 为并发度设置可配置上限，按 NAS 能力与 Wi-Fi 实测选择；连接建立、认证和服务端限流可能使高并发无收益。现有上传连接已关闭，不能直接复用，除非重构连接生命周期并实证复用安全。
- 另行评估是否存在可信 SMB 服务端校验接口；只有服务端计算的是实际远端文件字节摘要且响应受信任时，才能替代客户端完整回读。不能假定普通 SMB 写成功响应提供内容哈希。

**P3 — 远端多连接区间回读（已转正，默认 4）**

- 新增纯算法文件 [range_hash_sequencer.dart](file:///e:/Code/Projects/MiPix/app/lib/services/range_hash_sequencer.dart)（无 SMB / Flutter 依赖）：
  - `planRanges({total, rangeBytes})`：把 `[0, total)` 切成连续、无洞、无重叠的区间，末段吃余数。
  - `RangeHashSequencer`：按「期望偏移」重排乱序到达的数据，只通过注入回调按偏移升序 emit 进**唯一** `sha256` sink。`offset < expected`（重复 / 重叠）、越界、超过 `maxOffsetLead`、超过 `maxBufferedBytes` 一律 fatal 并 `aborted`；**内存有硬界，不随文件大小增长**。
  - `RangeScheduler`：按偏移升序派发、并发度受限；配合上述上界，最坏乱序缓冲 = `并发数 × 区间长度`（可计算）。
- `smb_service.dart` 新增 `_hashRemoteRangeVia(config, tempFull, {expectedSize, concurrency, onPhase})`：`createConnection` × N，每条连接用 `openRead(start, end)` 读一段，每段沿用 `stream.timeout(_stallTimeout)` 看门狗并处理 SMB 短读（按真实读到的字节推进偏移，缺口即抛错）。读前校验远端 `size == expectedSize`，结束后要求 `isComplete` 且 digest 非空；任一段失败 / 短读 / 超时 / 顺序异常均返回 `null`，由 `_verifyUploadedTemp` 走既有「删临时文件 + 抛错，绝不 rename」路径。**返回前必定关闭全部回读连接**（服务端会因未关闭的句柄拒绝 rename）。
- 开关 `static const int rangeReadbackConcurrency = 4`（**已转正、默认开启多连接区间回读**；`0` 仍保留单连接 `_hashRemoteVia` 路径，`>1` 才改走区间回读）。区间粒度 `rangeReadbackRangeBytes = 4 MiB`（区间内仍按 ≈64 KiB 分块，只是不再每块重开句柄）——按审阅意见，1 MiB 粒度会让 1.4 GiB 文件付出约 1400 次句柄开关，故 4 MiB 为本次取值。

### 13.11 故障注入（判据⑤）实测与「重试路径卡死」缺陷（2026-10-17）

**方法**：客户端侧用 `svc wifi disable` 注入「连接丢失」（等价于断网 / 服务端瞬断），在**上传段中途**与**校验段中途**各注入一次；恢复网络后走「重试失败」验证可恢复性。判据要求：任一注入都不得 rename、需正确处理 `.mipixtmp`、且任务可重试。

**注入 A — 上传段中途断 Wi-Fi**
- 上传在 395.7 MB / 703.7 MB 处中断；**未 rename**（rename 仅在校验通过后执行，上传阶段不 rename），临时文件保留待重试 —— 行为符合设计。
- Wi-Fi 恢复后批次内不自动续传（设计如此），需走「重试失败」。

**注入 B — 校验段中途断 Wi-Fi（P3 区间回读 4 连接进行中）**
- 约 1 秒内触发 `range read error: errno 103` → `[backup][verify] range FAIL ok=false complete=false consumed=12544512 expected=703742069` → `[backup][verify] FAIL remoteHash=null` → **未 rename**。fail-closed 正确。
- 恢复网络后重试：`fit_b` / `fit_c` 完整重传 + 校验 OK + rename 成功，摘要与源文件一致（`d7fd26f6…`）——**可重试验证通过**。

**判据⑤裁决（更新）**：断网注入下「不 rename + 清理 / 保留临时文件 + 可重试」**已覆盖并满足**（上传段、校验段各一次）。「停 Samba 服务」「服务端短读（少发字节）」两项仍建议在可控 SMB 测试端补充，如实标为未覆盖。

**新发现缺陷 — 重试路径 setup 调用缺卡死超时（真实复现「服务端锁死」）**
- **现象**：注入 B 遗留的僵死 SMB 会话在服务端**持锁**（对应 `MiPixFITest/fit_a.mp4.mipixtmp`——注入 A 写满 703 MB 的孤儿临时文件）。随后重试 `fit_a` 时，`[backup][hash]` 预取正常完成后**再无任何日志**，3+ 分钟不恢复；进程仅剩 2 条空闲 445 连接，无报错、无超时。两次重试均稳定卡住。
- **根因**：上传 / 校验主流程的每次 SMB 调用都有 `_stallTimeout` 看门狗，但**上传前的 setup 阶段**（删除旧 `.mipixtmp` / 建目录 / `createFile` / `setFileTime` 等）**未纳入该超时保护**——服务端因锁未释放而不回 ACK 时，这些 await 会被无限挂住（与「WiFi 静默断开导致 flush 挂死」同类），表现为「传输卡死且无日志」。
- **影响**：`.mipixtmp` 是防脏数据的正确机制；但当服务端残留锁未释放时，会**阻塞后续重试**，需人工重启 Samba 或手动删除孤儿临时文件才能恢复。
- **修复建议（待实施、本次不改代码）**：把 setup 阶段的 `delete` / `createFile` / `setFileTime` 等调用统一包进 `_stallTimeout` 看门狗（或独立的 setup 超时），超时即 fail-closed 抛错、任务可再次重试；批次启动前可对同名 `.mipixtmp` 做一次带超时的清理探测，探测失败即标记「服务端锁占用」并跳过、提示用户。
- **当前处置**：待 NAS 侧重启 Samba（或手动删除该孤儿 `.mipixtmp`）后复验 `fit_a` 收尾。
